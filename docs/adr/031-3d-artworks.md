# ADR 031：藝術模組加入立體作品（雕塑、建築）——多角度建檔、依作品類型分流辨識

- 日期：2026-10-08
- 狀態：提議（草稿，分支 `feat/立體作品`）。文末「待決定」列的事情決定之後才動工；畫作的辨識流程不在這份的改動範圍內
- 由來：`問題/專案問題.md` Q-2026-10-05-06（立體器物小實驗，追問 1–12）、Q-2026-10-08-04 與追問（個人工作流程檔，不在 repo 裡）

## 背景
藝術模組的每一層都假設作品是「一張平面的畫」：

| 地方 | 假設 |
|---|---|
| `shared/schemas/artwork.schema.json` | 一件作品一張圖（`image.path`）；`collection`（典藏單位）必填 |
| 索引（`index_store.py` 的 `image_vecs`、`pg_index_store.py` 的 `artworks.image_vec`） | 一件作品一個 CLIP 向量 |
| `search_service.identify()` → `verify.match()` | 第二階段 ORB＋RANSAC **homography**：只描述同一個平面換角度看的對應；退化檢查（`_degenerate`）的門檻照正面拍的畫校正 |
| 照片建檔（ADR 013）`intake_service._intake_stream()` | 一次收一張；清晰度 `page.blur_score()` 算整張照片 |
| 色彩分析（ADR 010）、影像對位（ADR 012） | 整張圖都是畫面；對位只適用平面 |
| 提示詞與錯誤訊息 | 「這幅畫」「知識庫中沒有這幅畫」 |

拍雕像、建築進來，現在會安全地回「知識庫中沒有這幅畫」（The Met Dataset 的器物、雕塑觀眾照片 926 張，0 張被認成畫，ADR 002），
但收進知識庫之後也認不出來。

### 已經量過的（2026-10-05～08，資料與腳本在 `data/met_3d/`，不進 git）
**立體器物**：The Met Dataset 的觀眾照片 915 張（長邊 500 px），拍到 666 件器物；知識庫用 Met 開放 API 的
`primaryImage`＋`additionalImages`（每件最多 8 張，共 2,504 張）。未收錄用 leave-one-out。認對率都是「0 認錯、0 未收錄被認錯」下的數字。

| 做法 | 雕塑 364 | 其他器物 438 | 近平面 113 |
|---|---|---|---|
| 現在：CLIP＋ORB＋H，館藏圖 1 張，前 3 名，門檻 20 | 9.9% | 12.6% | 53.1% |
| 多角度：CLIP＋ORB＋H，館藏圖多張，前 10 名，門檻 12 | 21.7% | 20.8% | 70.8% |
| CLIP＋ALIKED／LightGlue＋基礎矩陣（F，1 px），門檻 100，同組感知 | 40.1% | 36.5% | 81.4% |
| DINOv2 ViT-B/14＋ALIKED／LightGlue＋F 1 px，門檻 40，同組感知 | **69.2%** | 57.1% | 93.8% |

- **瓶頸是配對，不是幾何模型**：雕塑照片和正解任一張館藏圖有 ≥ 20 個配對的，ORB（ratio test）33.5%，ALIKED＋LightGlue 90.9%。
  只把 ORB 換成基礎矩陣反而變差（錯的配對也跟著變多）；換成 LightGlue 之後，F 才贏過 H（全部照片 F1 43.5% 對 H 34.9%）。
- **多角度有用**：對得上的照片有 35% 是靠第 2 張以後的館藏圖。
- **兩關要一起換**：只換第一階段（DINOv2＋ORB）全部照片 29.3%（現在 27.0%），幾乎沒變；只換第二階段時，22% 的正解根本沒進 CLIP 前 10 名。
- **成對、成套的器物**：一對水壺托盤（Met 460169／460170）F1 185、〈英雄掛毯〉的不同片段 83。
  不把它們標成「同一組」的話，所有組合的門檻都會被撐到 200，認對率只剩 26–30%。**知識庫要有「同組」欄位。**
- 長得像的不同件（埃及石雕的臉、主教像和國王像）F1 30–40，門檻 40 以下的錯配大多是這類。
- 館方附加圖偶爾是展廳照（背景有別件館藏），〈射手座之戰〉掛毯對到〈聖奧古斯丁〉的展廳照 F1 90。

**畫作不能跟著換第二階段**：同一套 ALIKED／LightGlue＋F1 ≥ 40 用在畫作，別版、習作、同系列 143 張有 75 張被認成知識庫的畫
（梵谷〈麥田與絲柏〉倫敦版對大都會版 F1 91–101，ORB 只有 0–6）。要兩邊都 0 認錯得把門檻拉到 200，畫作原圖認對率會從 71% 掉到 64%。
學習式配對會對上「構圖一樣」的不同件，ORB 不會；ADR 002 靠的正是 ORB 這個特性。只換第一階段（DINOv2＋ORB）畫作可以：0 認錯，71% → 80%。

**速度**（CPU，筆電 i5-9300H，中位數）：現在一次查詢約 0.29 秒；DINOv2＋ALIKED／LightGlue 的立體器物（前 3 件約 11 對）5.6 秒（長邊 448、1,024 點）～9 秒（672、2,048 點）。
GPU（GTX 1650）上約 1 秒。展示機 MacBook Air M5 沒量。後端的 embedding 一律跑 CPU（`config.py` 的 `embed_device`，為了各平台結果一致）。

**記憶體**：DINOv2 ViT-B/14 346 MB、ALIKED 的 LightGlue 48 MB、ALIKED-n16 2.7 MB；知識庫每張圖的 ALIKED 特徵點約 1 MB（2,048 點，ORB 不存）。

**自己拍的多角度**（純喫茶紙盒：5 張進知識庫、斜 45° 的 1 張測試，干擾項 666 件）：現在的 CLIP＋ORB＋H 認得出來，
只靠正面照的 31 個 inlier；另一張正面照 20 個對的 inlier 被畫作的透視檢查擋掉（|h31| 0.0051 > `verify_max_persp` 0.002）。
斜拍立體物件本來就有強烈透視，畫作的退化門檻不能照搬。

**領域路由（ADR 007）**：雕塑照片 364 張用現在的原型 100% 判成畫作（margin −0.38～−0.08，門檻 ±0.05），其他器物 98%；
把 5～666 件器物的主圖加進畫作原型，結果一樣是 100%（`data/met_3d/vecs.npz` 的 CLIP 向量，2026-10-08 量）。
桌上拍的紙盒 6 張則全部「不確定」（−0.047～−0.009，照規則當成圖紙）：路由擋的是商品照，不是雕塑。**建築沒有量過。**

**照片建檔的清晰度**：紙盒 6 張有 5 張被擋（整張 0.301–0.403，門檻 0.30），盒子那一塊只有 0.229–0.309；
拉高分數的是失焦的背景（螢幕那一條 0.32–0.48）。雕像、建築一定有展廳或天空當背景。

## 範圍
- **第一版：雕塑與立體器物**（可以環繞拍的東西）。實驗資料都在這一類。
- **建築先只留欄位、不宣稱認得出來**：完全沒有評估資料。立面接近平面，現在的 ORB＋H 可能對正面照片部分有效；
  但建築有尺度（整棟 vs 局部）、天氣光線、遮擋、人群的問題，正式做法是地標辨識（檢索＋空間驗證），要另外收評估照片再決定。
- 畫作的辨識流程不動（第一階段要不要加 DINOv2 另外決定，見「注意」）。

## 決定（提議）

### 1. 資料格式：留在畫作的知識庫，加作品類型與多角度
選項：
1. **`kb/artworks/` 加欄位**：問答、畫作頁、區域標註、建檔、權限全部沿用，靠 `kind` 決定哪些功能開。
2. 另開一個領域（`kb/objects/`，像圖紙那樣）：互不干擾，但問答、頁面、建檔、路由都要複製一份；使用者要的是「進藝術模組」。

採用 1：
```json
{
  "kind": "sculpture",
  "image": { "path": "kb/images/met-12345.jpg", "license": "CC0" },
  "views": [
    { "path": "kb/images/met-12345-v1.jpg", "license": "CC0", "label": "左前 45°" }
  ],
  "group": { "id": "met-lehman-tray-pair", "label": "一對水壺托盤" },
  "location": { "zh": "…", "en": "…" }
}
```
- `kind`：`painting`（預設；現有資料不用改）、`sculpture`、`architecture`。器物（瓶、盔甲）先歸 `sculpture` 的流程，要分開再加。
- `image` 仍是主圖：縮圖、色彩分析、區域標註座標、問答附圖都用它。`views` 是其他角度，畫作沒有。
- `group`：成對、成套的作品。辨識配到同組的另一件時回答「這是〈X〉，同一組還有〈Y〉」，不算錯也不算對。
- `collection` 只對 `painting`、`sculpture` 必填；`architecture` 改成 `location` 必填（JSON Schema 的 `if`／`then`）。
- 驗證（`kb.validate_kb`）：`views` 的圖都要存在；授權規則和主圖一樣；同一個 `group.id` 至少兩件。

### 2. 索引：每個角度一個向量，排名取同一件的最大值
- 檔案索引多存 `view_vecs.npy`＋每列屬於哪一件；PostgreSQL 多一張 `artwork_views`（`artwork_id`、`view_no`、`image_vec`）。
  `search_images()` 回傳「每件取各角度最高分」，介面不變。
- 領域路由的原型只用主圖（上面量過：器物主圖加進畫作原型，雕塑照片照樣 100% 判成畫作）。
- 立體作品的 ALIKED 特徵點（第 2 步）建索引時先算好存檔，查詢時只讀候選那幾件。

### 3. 辨識：依「候選作品的類型」選驗證方法，不靠路由分
選項：
1. 路由加第三類「立體作品」（CLIP 原型）：多一個會判錯的關卡，而且雕塑照片和畫作照片在 CLIP 上的距離沒量過。
2. **照候選的 `kind` 選**：候選是畫作就用現在的 ORB＋H（ADR 002 的門檻一個都不動），是立體作品就每個角度都驗、用立體作品的方法和門檻。

採用 2。設定放 `shared/models.yaml` 新的一段（數值照實驗，進系統前要重新校正）：
```yaml
object_retrieval:            # kind 是 sculpture／architecture 的候選
  verify_top_n: 10           # 展示規模（幾件到幾十件）：每件都驗
  method: orb_h              # 第 1 步 orb_h；第 2 步 lightglue_f
  verify_min_inliers: 12     # orb_h：館藏多角度、前 10 名、0 認錯的最低門檻；lightglue_f 是 40
  verify_max_persp: 0.01     # 斜拍立體物件的透視比畫作強（紙盒正面斜拍 0.0051）；要用評估資料重定
```
- `identify()` 回傳加 `kind`、配到的是第幾個角度、同組的另一件。
- 要量跨類的錯：畫作照片對到立體候選、立體照片對到畫作候選。

### 4. 分三步做
1. **第 1 步：格式、多角度、建檔（不加新模型）**：決定 1、2、3 和決定 5、6；立體作品的驗證先用 ORB＋H 多角度＋自己的退化門檻。
   館藏照的認對率只有約兩成（上表第 2 列），但安全（0 認錯），而且格式、建檔、索引第 2 步都用得到。
   自己有系統地拍（4 面＋4 個角，每 45° 一張）應該比館藏照好，**沒量過**，第 1 步的評估要量。
2. **第 2 步：立體作品的第二階段換 ALIKED＋LightGlue＋基礎矩陣（F，1 px）**：
   - 新相依：`cvg/LightGlue`（程式與權重 Apache-2.0；ALIKED BSD-3-Clause；SuperPoint 是非商業授權，不用）。
   - 只用在 `kind` 不是 `painting` 的候選；記憶體管理（ADR 006）把兩個模型加進可釋放清單。
   - CPU 上一次 5–9 秒（筆電量的），要嘛接受、要嘛允許這兩個模型走 GPU（和 `embed_device` 一律 CPU 的原則衝突，見待決定 3）。
3. **第 3 步：第一階段加 DINOv2 ViT-B/14（CLS，長邊 448）**：立體作品上百件以後才需要；
   幾件到幾十件時每件都驗，第一階段換什麼都一樣（實驗：CLIP 前 10 名 77.6% → DINOv2 94.4%，666 件）。

### 5. 照片建檔（ADR 013 的畫作那一半）
- 先選作品類型；立體作品一次收多張：主圖 1 張＋其他角度（建議環繞每 45° 一張，最多 8 張），每張都檢查清晰度、都比對「知識庫還沒有」。
- 清晰度改成只算主體：先試「畫面中間 60%」或「最清楚的一半區塊」，用 2026-10-03 的模糊模擬照（0.345–0.448）和紙盒照片校正，
  模糊照要照樣擋得下來。畫作沿用整張（門檻是照它校正的）。
- 表單欄位依類型：雕塑的材質（青銅、大理石）、尺寸（高 × 寬 × 深）；建築的建築師、地點，沒有典藏單位與館藏編號。
- 館方附加圖的展廳照不要收（背景有別件作品會造成錯配），建檔頁提醒；自己拍的背景盡量單純。

### 6. 依類型開關的功能
| 功能 | 畫作 | 立體作品 |
|---|---|---|
| 色彩分析（ADR 010） | 照舊 | 不算（背景顏色會混進去） |
| 影像對位（ADR 012） | 照舊 | 不做（只適用平面） |
| 畫作卡風格推測（ADR 018） | 照舊 | 照舊（器物、雕塑提示已經擋下 184/190） |
| 區域標註（ADR 030） | 照舊 | 可以，座標綁主圖 |
| 問答 | 照舊 | 作品卡多寫類型、材質、地點；「這幅畫」改成依類型的稱呼 |
| 兩件並排比較（ADR 017） | 照舊 | 欄位依類型 |

「這幅畫」散在後端（`chat_service.py`、`intake_service.py` 等 6 個檔 8 處）、前端（9 個檔 15 處）和共用層（`error_codes.md`、`agent.yaml`、`models.yaml`、`openapi.json` 6 處），
要改成依類型的稱呼。回答的提示詞（`answer_v4`）是組員 C 維護的，改了要跑 `make eval`。

## 驗收（每一步合併前）
- **畫作不能變差**：`make eval-met-photos`（2,467 幅：Flickr 原圖 71%、認錯 0）、`make eval-versions`（別版 0/143 被認錯）結果和現在一樣。
  畫作的流程沒動，數字應該完全相同。
- **立體作品**：把 `data/met_3d/scripts/` 的實驗整理成 `eval/run_object_eval.py`＋`make eval-objects`（雕塑／其他器物／近平面分開、同組感知），
  0 認錯、0 未收錄被認錯。
- **自己拍的**：每件環繞 8 張進知識庫，測試照每件 10–20 張（各角度、局部、不同背景與光線、拿在手上），干擾項放長得像的東西（同牌子別的口味、同類雕像）。
- **跨類**：畫作照片對立體候選、立體照片對畫作候選，0 認錯。
- **速度**：學校電腦、筆電、展示機各量一次查詢時間。

## 注意
- 實驗的門檻（ORB 12、F1 40、展廳 0.5）是用同一批 915 張照片挑的，略為樂觀；知識庫只有 666 件，變大後第一階段召回會下降（畫作 2,467 幅時 CLIP 前 3 名剩 79%）。
- 畫作的第一階段加 DINOv2（71% → 80%，每次查詢 CPU 多約 0.8 秒）是另一個決定，不在這份 ADR 裡。
- 動到共用層：`artwork.schema.json`、`openapi.json`（作品摘要加 `kind`、`views`）、`models.yaml`（`object_retrieval`）、
  `error_codes.md`、提示詞。照 `shared/CHANGELOG.md` 通知要跟著改的人；換 embedding 模型（第 3 步）要先在週會宣告、全量重建索引並重跑評估。
- 照片上傳會去掉 EXIF（`preprocess.to_jpeg_bytes`），所以建築不能靠照片的 GPS 判斷位置；要用位置當提示，得另外徵得同意。

# ADR 003：工廠機械加工圖領域與 Ortho2CAD 3D 重建

- 日期：2026-09-30
- 狀態：採用（demo）

## 背景
專題定位是「地端部署＋資料隱私」，目標客群包含製造業。畫作是公開資料，說服力有限；
工廠的加工圖、製程與檢驗規範才是真正不能外流的資料。所以用同一套架構（辨識 → 檢索 → 本地生成）
加一個「工廠機械加工圖」知識庫，並加上製造業特有的需求：**把二維三視圖還原成可編輯的 3D 模型**。

## 選項（圖紙 → 3D）
1. 一般 VLM（Qwen3-VL、雲端大模型）直接寫 CadQuery：論文中未微調的開源模型 IoU 明顯較低；雲端違反定位。
2. 傳統演算法（由三視圖做線框重建）：只適合乾淨的向量圖，對照片與隱藏線很脆弱。
3. **Ortho2CAD**（Joglekar et al., arXiv 2607.08891）：Qwen3-VL-8B 以三視圖→CadQuery 微調
   （SFT＋以 IoU 為獎勵的 RL），輸出可執行、可編輯的參數化程式碼。

## 決定
採用 3，並保留 1 當對照組（前端可切換「Qwen3-VL 4B 未微調」）。

- **權重**：論文作者沒有公開權重，使用 Hugging Face 第三方版本並固定 commit（見 `pipelines/setup_ortho2cad.py`）。
  GGUF（Q4_K_M）只含語言模型；訓練時 `tune_mm_mlp=True`，投影層有微調，不能用原版 mmproj，
  所以只以 HTTP Range 下載 `model.visual.*`（1.15 GB）自行轉成 mmproj。
- **推論**：Ollama 目前不能轉 Qwen3-VL 的 safetensors，改用 llama.cpp 的 `llama-server`
  （OpenAI 相容介面，`make ortho2cad`），沿用本專案「本地策略只准連本機／內網」的 provider 檢查。
- **輸入分布**：照官方 `pythonocc_for_step_to_ortho.py` 移植成 CadQuery／OCP 的產生器
  （`app/cad/drawing.py`），知識庫圖紙與「重建結果的回投影」都用它畫；送模型前裁掉標題欄、
  縮到訓練時的 `max_pixels=50176`（224×224）。
- **尺度**：模型輸出 DeepCAD 正規化尺度（約 0–1），依圖紙標註的外形尺寸等比縮放回 mm；
  未收錄圖紙由本地 Qwen3-VL 讀圖上的三個尺寸（兩個模型分工：Qwen3-VL 讀字、Ortho2CAD 建模）。
- **安全**：模型產生的是 Python 程式碼。AST 白名單（只准 cadquery／math、禁底線屬性與匯出入）→
  受限內建函式的子行程（CPU／檔案大小上限、不帶環境變數）→ macOS `sandbox-exec` 禁網路、
  只准寫入工作目錄 → 逾時砍掉。
- **圖紙辨識**：沿用 ADR 002 的兩階段，但圖紙版面都一樣，實測不同圖紙會在標題欄（連材料文字都相同）
  與尺寸數字上對上 300 個以上的點。改為：知識庫圖紙只在三視圖幾何區抽特徵點、排除退化的 homography
  （det≈0 或 >6），再把照片拉正比對線條重合度（F1）。
- **評估指標**：論文的 IoU（質心＋慣性主軸對齊、正規化尺度），另加「不旋轉」候選；體積改用體素計算，
  因為模型產生的實體常有細微瑕疵，OCC 布林交集會默默回傳 0（兩塊幾乎相同的板子算出 0.09）。
  另報「外框對齊 IoU」（重建結果外框對齊到圖紙標註尺寸）當工程上較直觀的參考。
  無效的實體先用 ShapeFix 修復再匯出與計算（未修復時同一份程式碼的 IoU 從 0.73 掉到 0.12），前端標示「已自動修復」。

## 結果（MacBook Air M5 16 GB，模擬實拍照，2026-09-30）
- 圖紙辨識：同圖紙 inlier 41–1376、線條重合 ≥ 0.60；不同圖紙（inlier ≥ 25 者）重合 ≤ 0.48。
  Top-1 100%（30 張，6 張圖紙 × 5 種拍法），未收錄拒答 100%（30 張，含版面相同的 5 張未收錄圖紙與治具定位板）。
- 3D 重建（6 張知識庫圖紙）：Ortho2CAD 可執行率 100%、平均 IoU 0.54（外框對齊 0.71）；
  未微調的 Qwen3-VL 4B 可執行率 17%、平均 IoU 0.07。板件、法蘭、軸承座表現好，
  軸類（車削件）與 T 形截面較弱——訓練資料 DeepCAD 以草圖擠出件為主。逐件數字見 README「評估」。
- 延遲：一張圖紙 700–3,000 token，時間約 98% 花在生成；前端逐字串流程式碼。Q4_K_M 冷機約 24 token/s（約 30–125 秒），
  連續運算數分鐘後因無風扇降頻到約 15–18 token/s（上面的評估即是，約 45–200 秒）。
  ~~與 Qwen3-VL 同時載入時約 15 token/s~~：事後以控制變因重測，是誤判，見下方「延遲的控制變因」。

## 嘗試過但未採用：限制座標小數位數（2026-09-30）
**動機**：重建時間約 98% 花在生成程式碼（首字約 0.6 秒、沙箱執行＋IoU 2–4 秒）。模型學的是 DeepCAD 轉出來的
程式碼，座標照 Python 浮點數原樣列印（`0.8281249999999999`），Qwen 分詞器一位數字一個 token：6 張圖紙的輸出
token 有 59% 是數字，小數第 5 位以後佔 32%。想法是用 llama-server 的 GBNF grammar 把小數限制在 4 位，省下這三成。

**過程**：只擋「第 5 位數字」不夠，模型會繞路接著寫：改寫全形數字（`0.2526３157…`）、該接 `)` 的地方接 `,`
（`lineTo` 多一個參數）、寫出亂碼讓括號對不上（語法錯誤）、改用科學記號（`0.6015e-05`，零件縮成一條線）。
最後把 grammar 照模型的輸出格式逐行寫死（歷來 16 份輸出只有 10 種行，15 份完整輸出截到 4 位後全部符合）：

```
root    ::= "import cadquery as cq" ( "\n" line )* "\n"?
line    ::= comment | plane | loop | solid | combine
comment ::= "# Generating a workplane for sketch " idx
plane   ::= "wp_sketch" idx " = cq.Workplane(cq.Plane(" vec ", " vec ", " vec "))"
vec     ::= "cq.Vector(" num ", " num ", " num ")"
loop    ::= "loop" idx "=wp_sketch" idx ".moveTo(" pt ")" ( ".circle(" num ")" | seg+ ".close()" )
seg     ::= ".lineTo(" pt ")" | ".threePointArc((" pt "), (" pt "))"
pt      ::= num ", " num
solid   ::= "solid" idx "=wp_sketch" idx ( ".add(loop" idx ")" )+ ".extrude(" num ( ", both=True" )? ")"
combine ::= "solid=solid" idx | "solid=solid." ( "union" | "cut" | "intersect" ) "(solid" idx ")"
idx     ::= [0-9] | [1-9] [0-9]+
frac    ::= "." [0-9]{1,4}
num     ::= "-"? ( [0-9] frac | [1-9] frac "e-" [1-9] [0-9] )
```

**結果**（同 6 張知識庫圖紙，temperature 0；原始檔 `eval/runs/experiments/20260930T131242-max-decimals-4-cad.json`）：

| 圖紙 | 輸出 token（不限→限 4 位） | 草圖數 | IoU | 外框對齊 |
|---|---|---|---|---|
| L 型固定支架 | 2,372 → 4,096（寫到上限） | 11 → 24 | 0.28 → 0.34 | 0.81 → 0.84 |
| 連接法蘭 | 709 → 555 | 2 → 2 | 0.81 → 0.87 | 0.82 → 0.85 |
| 階梯傳動軸 | 1,095 → 1,284 | 5 → 8 | 0.29 → 0.64 | 0.33 → 0.70 |
| 步進馬達安裝板 | 2,969 → 2,712 | 3 → 2 | 0.85 → **0.00** | 0.92 → 0.00 |
| T 型槽螺帽 | 2,042 → 2,607 | 9 → 11 | 0.29 → 0.33 | 0.49 → 0.36 |
| 立式軸承座 | 1,773 → 2,797 | 7 → 14 | 0.70 → 0.35 | 0.89 → 0.53 |
| **合計／平均** | **10,960 → 14,051（+28%）** | | **0.54 → 0.42** | **0.71 → 0.55** |

數字變短了，但模型的輸出分布整個被改變：多數圖紙會多寫草圖、甚至停不下來，總 token 反而多 28%；幾何有好有壞
（階梯軸變好、安裝板的長圓孔整個畫壞），平均 IoU 下降。（A/B 時量到約 18 token/s，事後以控制變因重測，確認是機器連續運算發熱降頻；同一時段 grammar 與不限制的解碼速度只差約 3%，grammar 本身不是變慢的原因。）
**結論：不採用。** 微調模型對訓練時的輸出格式（含數字長度）很敏感，要縮短輸出得從訓練資料著手（例如轉換時先四捨五入
再微調）。不改變輸出內容的加速（散熱、避免與問答同時生成、較高記憶體頻寬的硬體）才是可行方向；推測解碼在 Metal 上並非逐字相同，見下文。

## 延遲的控制變因（2026-09-30）
原本以為「與 Qwen3-VL 同時載入、記憶體吃緊」會讓速度從約 25 掉到約 15 token/s。在 demo 執行中（後端 :8000、
Ollama、llama-server 都開著）以同一張圖紙（階梯傳動軸，temperature 0）直接打 llama-server、讀它回報的解碼速度，
逐一改變一個條件重測：

| 順序 | 條件 | 輸出 token | 解碼速度 | 當下可用記憶體 |
|---|---|---|---|---|
| 1 | 閒置後第一次 | 1,095 | 24.6 | 72% |
| 2 | 一般 | 1,095 | 23.8 | 38% |
| 3 | grammar（限 4 位） | 1,284 | 23.1 | 38% |
| 4 | 一般（已連續運算約 3 分鐘） | 1,095 | **18.1** | 38% |
| 5 | grammar | 1,284 | 18.3 | 38% |
| 6 | Qwen3-VL 載入、閒置 | 1,095 | 17.7 | 6% |
| 7 | 經 demo 後端 `/cad/reconstruct` | 1,095 | 18.7 | 6% |
| — | 冷卻至 thermalState＝nominal | | | |
| 8 | 冷機、Qwen3-VL 載入、閒置 | 1,095 | **24.4** | 7% |
| 9 | 冷機、一般 | 1,095 | 24.4 | 7% |
| 10 | 同時有人問答（Qwen3-VL 生成 300 token，17 秒） | 1,095 | 16.4（總時間 45→67 秒） | 6% |

- **輸出 token 數與環境無關**：同一張圖紙在所有條件下都是 1,095（grammar 版都是 1,284），與先前各次評估相同。
  「輸出很長、過半是數字」這個主因不受 demo 是否執行影響。
- **變慢的真正原因是發熱降頻**：條件完全相同的第 2、4 輪，只差在連續運算了幾分鐘，速度就掉 24%（MacBook Air 無風扇，
  thermalState 由 nominal 轉為 fair）；冷卻後恢復 24.4。先前評估的速度也是一路下滑（16.3→14.2），與此一致。
- **記憶體吃緊本身不影響速度**：可用記憶體只剩 7%（Qwen3-VL 載入）時冷機仍是 24.4。
- **demo 後端沒有額外開銷**：經 `/cad/reconstruct` 與直接打 llama-server 速度相同（18.7 對 18.1–18.3）。
- **同時使用問答會搶 GPU**：問答那 17 秒重建幾乎暫停，整張多了約 22 秒。
- grammar 本身不會變慢（同一時段 23.1 對 23.8、18.3 對 18.1）。

現場展示前：不要緊接著跑評估（讓機器冷卻）、重建進行中不要同時問答、放在硬桌面或散熱架上；卸載 Qwen3-VL 沒有幫助。

## 嘗試過但未採用：n-gram 推測解碼（2026-09-30）
**動機**：程式碼重複性很高（每個草圖都重寫 `cq.Vector(3.749399456654644e-33, 1.0, -6.123233995736766e-17)`、
數字常有 `9999999` 長串），用 llama-server 的 `--spec-type ngram-*` 從已生成的內容猜下一段、一次驗證多個 token，
理論上 greedy 解碼的輸出不變。與圖片輸入可以並用。

**選設定**（階梯傳動軸，每輪先冷卻到 nominal）：不開 24.7 token/s；`ngram-simple`（預設 n=12、m=48）33.4（+35%）；
`ngram-map-k` 32.4；`ngram-mod` 30.7；`ngram-cache` 沒有產生草稿（24.8）；`ngram-simple` n=4、m=16 為 27.2 且輸出不同；
`ngram-simple,ngram-cache` 27.5 且輸出不同。

**完整評估**（6 張，經 demo 後端，兩輪都先冷卻；原始檔 `eval/runs/experiments/20260930T142023-spec-none-cad.json`、
`20260930T143242-spec-ngram-simple-cad.json`）：

| 圖紙 | 輸出與不開時相同 | IoU（不開→ngram-simple） | 耗時 |
|---|---|---|---|
| L 型固定支架 | ✗（第 4 行 `0.0633…` → `0.0573…`，之後寫到 4,096 上限） | 0.28 → **✗ 語法錯誤** | 106 → 94 秒 |
| 連接法蘭 | ✓ | 0.81 → 0.81 | 33 → 31 秒 |
| 階梯傳動軸 | ✓ | 0.29 → 0.29 | 57 → 45 秒 |
| 步進馬達安裝板 | ✗（第 18 行提早結束，少一個草圖） | 0.85 → 0.73 | 162 → 107 秒 |
| T 型槽螺帽 | ✗（第 14 行座標 `0.1669…` → `0.5003…`） | 0.29 → **✗ 幾何錯誤** | 114 → 60 秒 |
| 立式軸承座 | ✓ | 0.70 → 0.70 | 100 → 78 秒 |

輸出相同的 3 張快 7–22%，但 6 張中 3 張輸出不同、2 張失敗。原因：Metal 上驗證草稿是一次算多個 token（矩陣乘矩陣），
與逐一生成（矩陣乘向量、flash attention 的向量版）累加順序不同，浮點誤差讓幾乎同分的 token 翻轉；這個模型又像限制小數位數時
一樣，一個數字不同後面就整段走樣。不開時同一張圖紙每次輸出逐字相同（多次重現），所以差異確實來自推測解碼。
**結論：不採用。** 另一個啟示：單次 greedy 的逐件 IoU 對微小擾動很敏感，逐件數字不宜過度解讀，正式評估應增加圖紙數量或多次取樣。

## 注意
- 第三方權重的訓練細節（只有 SFT 或含 RL、哪個資料集）無法確認；報告引用論文數字時要註明不是同一份權重。
- 圖紙與製程文件是虛構的示範資料；模擬照由數位原圖加工。正式評估需真實列印／拍攝的圖紙，
  並重新校正 `drawing_retrieval` 的門檻。
- 16 GB 記憶體同時載入 Ortho2CAD（約 6.5 GB）與 Qwen3-VL 4B 很吃緊（可用記憶體約 6%、會用到 swap），雖然實測不影響解碼速度，
  但沒有餘裕再開其他程式；5070 Ti 主機或 32 GB 以上較適合，桌機有風扇也不會降頻。

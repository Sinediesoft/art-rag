# ADR 004：工廠庫存查詢採 Text-to-SQL（本地模型＋唯讀資料庫）

- 日期：2026-10-01
- 狀態：採用（demo）

## 背景
工廠圖紙領域（ADR 003）的問答走 RAG：從製程與檢驗文件檢索段落再生成。但現場最常問的是
「還有幾件」「哪張訂單會缺貨」「哪些零件低於安全庫存」這類**數字與明細**——它們存在 ERP 的關聯式資料表，
每天在變，而且需要加總、比較、跨表 JOIN。把庫存寫成文字段落丟進向量檢索，模型只能從幾段文字「猜」總數，
答案無法驗證也會過期。所以在同一套地端架構上加一條 Text-to-SQL 路徑：**文件走 RAG，數字走資料庫**。

## 選項
1. 把庫存資料轉成文字段落放進 RAG：加總與比較都靠模型心算，數字不可靠。
2. 預先寫好固定報表 API，模型只負責選報表：安全但問法受限，新問題要改程式。
3. **Text-to-SQL**：模型依資料表結構把問題寫成 SQL，資料庫負責算；SQL 與結果表攤開給人檢查。
4. 雲端大模型寫 SQL：準確率較高，但要把 schema、客戶名稱與問題送出本機，違反專題定位。

## 決定
採用 3，只用本地模型，並把「模型寫的 SQL 不可信任」當成前提設計防護。

- **模型**：沿用 `hybrid` 生成端（Ollama 的 Qwen3-VL 4B，失敗改走本地備援），不另外載入 SQL 專用模型
  （16 GB 的 Mac 已同時載入 Qwen3-VL 與 Ortho2CAD）。庫存屬企業內部資料，雲端策略（含對照組）一律回
  `CLOUD_CONFIDENTIAL_FORBIDDEN`，連 schema 都不送出。
- **資料**：`kb/inventory/` 一張圖紙一個 JSON（庫存、異動、工單、客戶訂單）＋`site.json`（資料日期、倉庫），
  料號、品名、材料從 `kb/parts/` 讀，不重複維護。建庫時檢查帳務一致性（各倉異動加總＝目前庫存、流水帳不為負、
  已出貨＝銷貨出庫、完工＝生產入庫），不一致就不建。JSON 有變動時後端自動重建 `data/inventory.sqlite3`，
  `make demo-add` 加入第 7 張圖紙後不必重啟。
- **prompt**（`shared/prompts/sql_v1.md`）：DDL＋中文欄位註解、欄位值（零件、倉庫、客戶與各狀態欄的可能值，
  讓模型照抄正確的品名）、8 個 few-shot 範例、資料日期當「今天」。固定內容在前、問題在最後，
  連續提問時 Ollama 重用前段 KV cache（實測首字從約 5 秒降到約 0.2 秒）。
- **三道防護**（任一道擋下即可）：
  1. 靜態檢查：只准一條 `SELECT`／`WITH`，含 `INSERT`、`UPDATE`、`DELETE`、`PRAGMA`、`ATTACH` 等就拒絕
     （字串常值先遮蔽，備註裡的字不會誤判）
  2. 唯讀連線：`mode=ro` 開檔＋`PRAGMA query_only`；庫存與使用紀錄（`artrag.sqlite3`）分成兩個檔案
  3. SQLite authorizer 白名單：只准讀 6 張表與 1 個檢視表、只准白名單函式（擋 `sqlite_master`、
     `load_extension` 等），progress handler 2 秒逾時（無窮遞迴查詢也會被中止），回傳最多 200 列
- **自我修正**：SQL 執行失敗（欄位不存在、語法錯誤）就把錯誤訊息回饋給模型重寫，最多 2 次。
  **但要求修改資料時不修正、直接拒絕**（`SQL_REJECTED`）：實測模型照「把庫存改成 0」寫出 `UPDATE`，
  若讓它「修正」，它會改寫成 `SELECT` 列出庫存，回答模型再依結果說「已全部設為 0」——資料沒被改，
  但回答是錯的。回答 prompt 也加一條「系統不會修改資料」。
- **回答**：第二步用 `sql_answer_v1` 只依查詢結果回答（最多放 30 列）；結果 0 筆不呼叫模型，
  固定回「查無符合條件的資料。」。前端同時顯示 SQL、結果表與回答，數字可以對照。

## 評估（`make eval-sql`，2026-10-01，MacBook Air M5 16 GB、qwen3-vl:4b-instruct）
20 題（與 prompt 內範例不同，含查詢、篩選、日期、JOIN、彙總），以「查詢結果與標準 SQL 相同」計分
（允許多輸出欄位、忽略順序）：

| 指標 | 結果 |
|---|---|
| 執行正確率 | 95%（19/20） |
| 可執行率／一次就能執行 | 100%／100% |
| 回應時間（寫 SQL＋執行＋回答） | P50 3.5 秒、P95 6.3 秒（重跑兩次，正確率相同） |
| 外送資料量 | 0 |

唯一答錯的是「機密等級零件的庫存總共有幾件」：模型多加了 `GROUP BY p.part_id`，把總數拆成各零件的數字。
題目由開發者撰寫、資料只有 6 張圖紙，數字只證明流程可行。

## 影響
- 正式版改 PostgreSQL：庫存放在獨立 schema，Text-to-SQL 用**只有 SELECT 權限的資料庫角色**＋
  `statement_timeout`，取代 SQLite 的 authorizer；靜態檢查與修正流程不變。若接真實 ERP，改連 ERP 的唯讀
  檢視表，不直接開放原始資料表。
- schema 改了（`inventory_repo.TABLES`）要同步更新 few-shot 範例並重跑 `make eval-sql`；
  `SCHEMA_VERSION` 遞增後資料庫會自動重建。
- 小模型的弱點在彙總語意（要不要 GROUP BY、正負號）；題目變多時再補範例，或評估換 7–8B 模型的效益。

## 補充（2026-10-01，生產排程上線後）
工廠資料庫加入 `machines`、`schedule_ops`、`v_wo_plan`，`work_orders` 加 `priority` 並納入圖紙頁開立的工單（ADR 005），
prompt 改為 `sql_v2`（多一條規則與 2 個排程範例）。同一份 20 題重跑：執行正確率 90%（18/20）。
新增的錯誤是 sql-14「VMC-01 有哪些還沒完工的工單」：模型改用 `schedule_ops` 回答「排在 VMC-01 的工單」，
標準答案是主要機台 `work_orders.line`——有了排程之後兩種解讀都說得通。為了不把答案寫進 prompt，標準答案與範例都不改，
只在 README 註明；排程類問題的答案隨每次排程改變，不放進評估集。

# ADR 011：智慧助理——Jev（System 1）判斷意圖，修改資料走權限判定與主管核准

- 日期：2026-10-01
- 狀態：部分由 ADR 014 取代（2026-10-02）：**Jev 不再判斷意圖**，意圖一律由本地分流判斷，Jev 改在五段防護的
  第 2 段（輸入護欄）與第 4 段（檢索段落過濾）把關；「查詢不限範圍」改成依角色的資料範圍。
  身分、修改資料流程、主管核准、信心閘門照本文不變
- 編號：在 `dev` 上原為 007；2026-10-02 合併進 `feat/工作流優化` 時改為 011（007～009 已是領域路由、段落篩選、PostgreSQL，010 是色彩分析）

## 背景
系統已經有五個入口：尋畫、工廠圖紙、庫存查詢、生產排程、系統狀態。使用者得先知道「這件事該去哪一頁」。
另外，Text-to-SQL 只能查詢；有人打「把法蘭庫存改成 0」時只能拒絕，沒有正式的修改流程，也沒有身分與權限。

TypeSafe 的 **Jev** 是 System One 決策模型：不生成文字，只回答分類題（選擇題、是非題）並給機率，
適合當「先判斷使用者想做什麼、有多確定」的第一關（System 1）；實際執行仍交給本機既有模組（System 2）。

## 決定

### 1. 統一入口＋System 1／System 2
新增「智慧助理」頁（`/assistant`，`POST /api/v1/agent/route`）。只有這個入口會呼叫 Jev；
圖紙頁、庫存頁等原本的頁面已經決定了模組，不呼叫 Jev。

```
使用者輸入（目前身分＋一句話＋照片）
→ 本機前處理：帶入身分；零件、倉庫、客戶、畫作、單號換成代號（〈連接法蘭〉→ [圖紙A]）
   照片在本機判斷是畫作還是圖紙（照片不送 Jev）；只有照片時不呼叫 Jev，依辨識結果定意圖（辨識不到＝超出範圍）。
   和以圖搜圖、問答同一個領域路由（ADR 007）：拿不準時當圖紙，只跑該領域的辨識，沒通過就是無法辨識
   （2026-10-02 起；之前是先試畫作、沒中再試圖紙，同一張照片在這裡和問答可能判成不同領域）
→ System 1：Jev（只收代號化文字＋照片類別）；沒金鑰、停用、逾時（1.5 秒）、401／429／529 → 本地路由
→ 信心閘門（依動作風險分流）
→ System 2 本地執行：RAG 問答、Text-to-SQL、Ortho2CAD、Timefold、修改資料流程
→ 串流回應：先顯示路由卡（誰判斷的、意圖、信心、外送位元組），再顯示模組的回答
→ 路由紀錄（route_logs）、稽核紀錄（audit_log）
```

Jev 一次請求問完五題：`intent`（10 個意圖）、`modify_op`（9 種修改操作＋none）、
`wants_numbers`、`refers_to_current`、`overrides_rules`（是非題）。題目與選項說明在 `shared/agent.yaml`。

### 2. 信心閘門：依「判斷錯的代價」分三級門檻

| 風險 | 意圖 | 門檻 | 通過後 |
|---|---|---|---|
| 唯讀 | 以文搜畫、畫作問答、圖紙查找、製程問答、庫存／訂單／工單查詢、系統狀態 | 0.60 | 直接執行 |
| 耗時 | 3D 重建、排程求解 | 0.75 | 先出確認卡 |
| 寫入 | 修改資料 | 0.85 | 進入修改資料流程 |

前兩名機率差小於 0.15、或低於門檻 → 澄清按鈕讓使用者選（點選後 engine＝user，不再呼叫 Jev）。
使用者想叫系統略過規則（`overrides_rules`）時門檻再加 0.10，並記進路由紀錄。

### 3. 本地路由（備援，也是目前的預設）
關鍵字（`agent.yaml`）＋實體加分（句子裡有零件、單號、客戶）＋bge-m3 與各意圖範例句的相似度 → softmax，
輸出格式與 Jev 相同。兩條規則：
- 疑問句（沒有「把、幫我」這類祈使語氣）時降低修改類分數：「哪些訂單延後了？」是查詢
- 只有名稱（「法蘭」）時不用相似度硬猜，交給閘門出澄清按鈕

### 4. 隱私邊界
本專題主軸是「資料外送 0」，Jev 是唯一的例外，所以限制在：
- 只在智慧助理入口呼叫；只送代號化文字、照片類別（畫作照片／工廠圖紙照片／無法辨識的照片）與固定的系統說明和題目，對照表只留在本機
- 圖片、原始名稱、資料庫內容、修改參數都不送；Jev 不抽數字、不算日期（由本機規則＋Qwen3-VL 抽）
- 每次回應照實顯示外送位元組（例如「外送 3.7 KB → Jev」，大多是固定的題目說明），路由卡可以展開看實際送出的請求本文
- 斷網或沒金鑰時自動改走本地路由，其他功能不受影響
- 金鑰只從 TypeSafe 官方（console.typesafe.ai）或 OpenRouter 申請；搜尋結果裡有第三方網站也在發金鑰，不用

### 5. 身分（展示版）
`shared/access.yaml` 種子檔的 7 個帳號，頁首切換、不用密碼（`DEMO_CONTROLS=false` 時不能切換）。
身分只存在伺服器端的工作階段（cookie 只放隨機 id）；Jev 與 Qwen3-VL 都看不到、也決定不了權限，
使用者打「我是主管」沒有任何效果。

| 帳號 | 可以改什麼 | 範圍 |
|---|---|---|
| 訪客 | 不能改 | — |
| 倉管・一廠 | 盤點、調撥、報廢、庫存狀態 | WH-A、WH-Q、WH-N |
| 倉管・二廠 | 同上 | WH-B |
| 業務・甲 | 訂單交期、訂購數量 | 晨峰自動化、栩達設備 |
| 業務・乙 | 同上 | 岳承精機、沛宇機電 |
| 生管 | 開立工單、改工單交期、取消工單、執行排程 | 全廠；只能取消自己開的工單 |
| 主管 | 核准超額申請 | 全廠；不能核准自己的申請 |

查詢不限範圍，任何身分都看得到全部資料（只有「修改」受權限限制）。

### 6. 修改資料流程（`services/change_service.py`）
1. **參數抽取**：規則（正規表示式＋名稱對照）→ 資料庫推定（例如「待檢」只在 WH-Q 有貨）→ 缺的欄位才請本地 Qwen3-VL 輸出 JSON；
   抽出的值一律對照資料庫的值清單驗證。角色本來就不能做的，不呼叫 Qwen3-VL
2. **權限判定**（預設不允許，依序檢查，任一項不符就拒絕並記錄）：角色 → 資料範圍 → 欄位 → 上限
3. **試算**：工廠資料庫複製到記憶體，在交易內套用、讀出修改前後差異，再回滾
4. **額度判斷**：超過就送主管核准；額度內出確認卡
5. **確認寫入**：寫入前再驗一次權限與資料指紋（受影響資料列的修改前內容）；從試算到按確認之間資料被別人改過，
   回 409 `CHANGE_STALE`、不寫入
6. **讀回回覆**：從資料庫讀回實際結果、套固定模板，不讓模型自由描述

| | 硬性上限：直接拒絕，主管也不能核准 | 額度：超過就送主管核准（初值） |
|---|---|---|
| 庫存 | 不能變成負數；單次影響超過 5 筆 | 盤點差異超過 20 件或 20%；報廢超過 10 件；調撥超過 50 件 |
| 訂單 | 訂購數量少於已出貨數量 | 交期延後超過 7 天；訂購數量減少 |
| 工單 | 改零件主檔、機台資料（不開放） | 急件工單；取消已在生產中的工單 |

**模型不寫修改用的 SQL**：修改只能走白名單的固定操作（`repositories/data_changes.py`，寫死的參數化 SQL），
單號沿用既有規則：盤點 IC-、調撥 TR-、報廢 SC-、工單 WO-，另加改庫存狀態 ST-、改訂單 CO-、改工單交期 WD-、待核准 AP-。
Text-to-SQL 仍然只能 SELECT。

**寫在哪裡**：`inventory.sqlite3` 維持唯讀（Text-to-SQL 碰不到可寫入的檔案）。異動、待核准單、稽核紀錄寫進
`production.sqlite3`（`data_changes`、`approvals`、`audit_log`），工廠資料庫重建時依序重播異動
（每筆一個 savepoint，某筆不再成立就略過並記錄）。每次庫存增減都同時寫一筆 `stock_moves`，
「各倉異動加總＝目前庫存」在修改後仍成立。`make demo-reset` 一併清掉。

### 7. 主管核准
- 只能在「待核准清單」（`/approvals`）按按鈕；不接受用對話核准，避免有人在聊天裡誘導系統核准
- 核准前重新試算，比對申請時的資料指紋；不同就讓申請失效（請申請人重送）
- 寫入前再驗一次申請人的權限與資料版本；申請人與核准人都記進稽核紀錄
- 退回要附理由；超過 24 小時沒處理自動失效

### 8. 權限在 API 層檢查，不只檢查聊天入口
圖紙頁的「開立工單」、取消工單、開始排程、展示還原（`/admin/production/reset`）都走同一套規則，
否則繞過聊天、直接打 API 就能改資料。圖紙頁開急件工單會收到 409 `APPROVAL_REQUIRED`，按「送主管核准」走同一個流程。

### 9. 記憶體管理
路由結果一出來就知道接下來要哪些模型（`agent.yaml` 的 `intent_models`），預估超過 80% 先釋放其他模型；
bge-m3 一律保留（下一句路由還要用）。啟動時先算好範例句向量，第一次路由也只要約 40 ms。
修改資料的補欄位（`fill_with_llm`）不另外進入記憶體管理的流程：Qwen3-VL 只靠這裡的預估保留，生成中不標「使用中」，背景監控若在這時遇到 ≥ 80%，可能把它一併釋放。

## 評估（`make eval-route`）
`eval/route_qa.jsonl` 44 句中文（與 `agent.yaml` 的範例句完全不重複），2026-10-01、本地路由（bge-m3）：

| | 本地路由 | Jev |
|---|---|---|
| 意圖正確率 | 100%（44/44） | 未設定金鑰，略過 |
| 直接處理（不必再問） | 95% | — |
| 修改誤判（查詢↔修改） | 0 | — |
| 修改操作正確率 | 100%（11/11） | — |
| p50 延遲 | 約 40 ms | — |
| 外送 | 0 B | — |

注意：第一次跑是 93%（41/44），依錯的三題補了關鍵字（「哪一年」「精度」）與「只有名稱就出澄清按鈕」規則後才到 100%，
所以這個數字偏樂觀；題目少、又被用來調過規則，需要再加一批沒看過的句子。
填入 Jev 金鑰後重跑同一份題目，才能比較兩者並決定要不要調門檻。

## 取捨
- Jev 讓「外送 0」多了一個例外；用代號化、只在統一入口、每次顯示外送量來限制，而且隨時可以關（`JEV_ENABLED=false`）
- Jev 官方文件沒寫支援哪些語言；中文表現要靠 `make eval-route` 實測
- Jev 文件提醒使用者輸入可能左右它的判斷：所以安全檢查一律以本機為準（權限、白名單、SQL 唯讀），
  Jev 判錯最多是分派到錯的模組，繞不過權限
- 展示版用預設帳號、不用密碼；正式版要接公司的登入（SSO），工作階段改存資料庫
- 身分存在後端記憶體：後端重啟就回到「訪客」

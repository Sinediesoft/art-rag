# ADR 007：領域路由（MMed-RAG 的領域辨識）

- 日期：2026-09-30
- 狀態：採用

## 背景
畫作與工廠圖紙各有一個上傳入口，使用者從哪一頁上傳就決定了走哪個領域：
在首頁拍了圖紙，會得到「知識庫中沒有這幅畫」，其實是另一個領域的東西；
API 只帶 `image_id` 的問答也一律當成畫作。

MMed-RAG（Xia et al., ICLR 2025）的 Domain-Aware Retrieval 先用一個領域辨識模組判斷影像屬於哪個領域
（放射、眼科、病理），再交給該領域專屬的檢索器；論文的消融實驗顯示，光是加上領域路由就提升 16–18%。
這個專案的各領域檢索器早就分開了（畫作走 `identify`，圖紙走 `identify_drawing`，各有自己的驗證關卡與 prompt），
缺的只有前面那一步。

## 選項
1. **微調分類器**（MMed-RAG 的做法：微調 BiomedCLIP）：需要標註照片；手上只有由數位原圖加工的模擬照，
   分類器容易學到加工痕跡而不是領域差異。
2. **零樣本文字提示**（「一幅畫作」vs「一張機械加工圖」）：95 張評估照片全對，但兩類間距只有 0.18。
3. **知識庫原型**：每個領域的知識庫圖片 CLIP 向量取平均（就是索引裡現成的 `image_vecs`），
   不用訓練、不碰評估照片，新增畫作或圖紙重建索引後原型自動更新。實驗全對，間距 0.43。

醫學影像各領域彼此很像，所以 MMed-RAG 需要微調；畫作和白底黑線的圖紙差異很大，原型法就夠了。

## 決定
採用 3（`backend/app/rag/router.py`）。
- `margin = sim(圖紙原型) − sim(畫作原型)`；`|margin| < router.min_margin`（`shared/models.yaml`，0.05）視為不確定，
  **一律當圖紙**：圖紙屬機密，走圖紙流程最壞只是不能用雲端對照組；反過來把圖紙當成畫作，就走進了允許雲端對照組的那條路。
- 新 API `POST /api/v1/search/any`：路由後只跑判定領域的辨識，照片與 CLIP 向量只算一次。
  原有的 `/search/image`、`/search/drawing` 不變，使用者強制指定領域時使用。
- 問答只帶 `image_id`（沒有 `artwork_id`／`part_id`）時先經過路由；SSE `sources` 事件多帶 `route`。
- 前端：畫作頁與圖紙頁的以圖搜圖都先經過路由，判定為另一個領域就轉頁並顯示提示，
  可按「不對？改用…辨識」強制指定領域。

## 結果（`make eval-router`，2026-09-30，Windows＋GTX 1650，`eval/runs/20260930T140809-7586-router.json`）
| | 張數 | 路由正確 | margin |
|---|---|---|---|
| 畫作照片（`eval/photos`） | 30 | 30 | ≤ −0.288 |
| 圖紙照片（`eval/drawing_photos`） | 65 | 65 | ≥ +0.140 |

兩類間距 0.428，沒有一張落在不確定區；`/search/any` 延遲中位數 567 ms（P95 665 ms，含辨識）。
端到端（路由＋辨識）94/95：唯一錯的 `unknown-02__crop.jpg` 是圖紙辨識本身誤收
（直接呼叫 `/search/drawing` 也一樣，線條重合度 0.557 剛好高於 `verify_min_overlap` 0.55；
同一張在 MacBook 上的評估是拒答），與路由無關。

## 注意
- 評估照片都是模擬照，也沒有「既不是畫作也不是圖紙」的照片（自拍、文件等）。換成真實實拍照後要重跑 `make eval-router`；
  要不要加第三類「都不是」（拒答），需要先收集這類照片看 margin 與兩個原型分數的分佈。
- 原型是平均向量：某個領域的內容變得很多樣時（例如加入大量不同畫風的畫），要重看 margin 分佈與 `min_margin`。
- 路由只看 CLIP 整體相似度，不取代後面的 ORB 幾何驗證與線條重合度。

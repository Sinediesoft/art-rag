# ADR 012：影像對位與比對（拍到哪一塊、哪裡不一樣）

- 日期：2026-10-02
- 狀態：採用（demo，第 1 步）
- 由來：`問題/專案問題.md` Q-2026-10-02-01 的追問（個人工作流程檔，不在 repo 裡）

## 背景
專案主打「通用型智慧助手」，但兩個領域共用、看得到的分析工具只有以圖搜圖。要找「程式寫一次、換領域只換設定」
的工具，而且畫作、工廠兩邊都講得出用途。影像對位與比對最符合：

- 畫作：照片拍到原畫的哪一塊（細節定位，Q-2026-10-01-04 第 1 項）；之後可以比複製品、修復前後；
- 工廠：手上這張圖紙（例如舊版的列印稿）和知識庫的圖紙哪裡不一樣——改版改了哪裡。

不用新模型、全 CPU：辨識那一步已經用 ORB＋RANSAC 算出照片 → 知識庫圖的單應矩陣 H（`verify.match()`），
圖紙辨識也已經用 H 把照片拉正來比線條（`ink_overlap()`），只是 H 用完就丟了。

範圍（使用者在 2026-10-02 選定「第 1 步」）：
- 共用核心（定位＋線條差異）、API、評估；
- 畫作只標位置，圖紙另外找不同；
- 結果放在以圖搜圖「辨識成功」卡片的下面，自動顯示（使用者選定）。

不在這一步：
- 具名區域（「你拍的是落款處」「差異在前視圖」）、問答優先取拍到區域的段落（第 2 步）；
- 兩張上傳照片互比（第 3 步）；
- 畫作找不同、近拍特寫（第 4 步，看評估再決定）。

## 選項
1. **獨立 API**：`GET /images/{id}/align?target=…`，前端在辨識成功後再呼叫一次（和色彩分析的 `PhotoColors` 同一種做法）。
   特徵點會重算一次（約 20 ms），但辨識流程完全不動；之後兩張照片互比、智慧助理都能直接用同一支。
2. 塞進辨識結果：`identify()` 已經有 H，直接在回應加位置框與差異。少一次請求，但以圖搜圖的回應格式要改、
   圖紙辨識變慢；疊圖 PNG 還是要另一支 API，第 3 步也還是要獨立 API。
3. 混合：辨識回應只加位置框，找不同走獨立 API。兩邊都要改，結果分散在兩處。

## 決定
採用 1（使用者選定）。

### 流程
```
以圖搜圖辨識成功 ─► GET /images/{id}/align?target=artwork:<id> ─► 位置框（原圖上框出拍到的範圍）
以圖搜圖紙辨識成功 ─► GET /images/{id}/align?target=part:<id>
     ─► ORB＋RANSAC 求 H（strict：排除退化的 H）─► 照片拉正到圖紙座標
     ─► 三視圖各一格：剛體微調位置 ─► 比線條（缺少／多出）─► 合併成幾處差異 ─► 疊圖 PNG
```

### 共用核心（`backend/app/analysis/align.py`，只用 numpy＋OpenCV，不碰索引與資料庫）
- `locate()`：用 `verify.match()` 的 H 把照片四角投到參考圖，回傳位置框（0–1）、拍到的面積比例、中心。
  - 對應點下限沿用各領域辨識的 `verify_min_inliers`：辨識過了就對得上，不會「辨識成功卻對不上」。
  - 位置框不合理就回 None：鏡像（det < 0）、角跑到相機後面、不是凸四邊形、面積小於參考圖 0.2% 或大於 25 倍。
  - 畫作不能用圖紙的 `_plausible()`：拍 30% 的近照縮放比例約 0.2，會被它當成退化。
- `diff_ink()`：拉正後比線條。
  - 只比給定的格子（圖紙是三視圖的方框 `verify.drawing_views()`，取自 `app/cad/drawing.py` 的 `POSITIONS`、`VIEW`）；
  - 每格各自用 ECC 做剛體微調（平移 ≤ 15 px、旋轉 ≤ 約 1.7°）；
  - 「缺少」＝圖紙有、照片附近 3 px 內沒有線（照片用寬鬆門檻 `faint_ink_c`）；
  - 「多出」＝照片有（嚴格門檻）、圖紙附近 3 px 內沒有；
  - 相距 24 px 內的區塊併成一處；
  - 差異超過圖紙線條 25% → `global_change`，不列區塊。
- `overlay_png()`：圖紙淡化，缺少塗紅、多出塗藍，每處框起來編號；沒比對的地方再淡一層。
  `location_png()`：畫作原圖上框出拍到的範圍，範圍外調暗。
- `verify.py` 抽出 `rectify()`、`ink_layers()`、`photo_ink()`、`ref_ink()`、`drawing_region()` 共用。
  `ink_overlap()` 的結果不變：改寫前後在 78 組（照片, 圖紙）上逐一比對，數值完全相同。

### 設定（`shared/models.yaml` 新增 `image_compare`，一個領域一份）
```yaml
image_compare:
  art:
    diff: none          # 只標位置
  mfg:
    diff: ink
    tolerance_px: 3
    min_region_px: 30
    merge_px: 9
    merge_gap_px: 24
    edge_margin_px: 12
    max_changed_ratio: 0.25
```
`faint_ink_c`（8）、`refine_max_shift_px`（15）、`refine_max_linear`（0.03）用程式預設值（`CompareSpec`）。
不影響索引，所以不進 manifest，改了不用重建。換領域＝換一份設定（加上那個領域的格子）。

### API
| 路徑 | 內容 |
|---|---|
| `GET /api/v1/images/{image_id}/align?target=artwork:<id>\|part:<id>` | `ImageAlignment`：`target`、`inliers`、`location`（`polygon`、`coverage`、`center`）、`diff`（畫作為 null；圖紙為 `status`：same／changed／global_change、`regions[]`：`bbox`、`kind`：missing／extra／both、`area_ratio`）、`reference_url`、`overlay_url`、`notes`、`latency_ms` |
| `GET /api/v1/images/{image_id}/align.png?target=…` | 疊圖 PNG，與上一支共用快取 |

- 兩支都是 GET：結果固定、沒有副作用。最近 32 組（照片, 對象）留在行程內。
- 純 CPU、不載入模型，不經過記憶體管理。
- 錯誤：
  - target 格式不對 → `VALIDATION_ERROR`；
  - 找不到 → 沿用 `IMAGE_NOT_FOUND`、`ARTWORK_NOT_FOUND`、`PART_NOT_FOUND`；
  - 新增 **`ALIGN_FAILED`**（422）：對應點不夠或位置框不合理，不硬畫。

### 前端（`frontend/src/components/align/AlignmentCards.tsx`）
- 以圖搜圖頁：成功卡下面「你拍到的位置」。
  - 原圖上用 SVG 畫出四邊形、範圍外調暗，附「照片拍到原畫約 27% 的範圍，在畫面的中央」；
  - 拍到 ≥ 90% 時只寫「照片拍到整幅畫」，不畫框。
- 圖紙辨識頁：成功卡下面「和知識庫圖紙（rev.B）的差異」。
  - 疊圖＋編號清單（缺少、多出、兩種都有）；
  - 沒差異寫「三視圖的線條一致」；整體變了只放提示，不放疊圖。
- `ALIGN_FAILED` 只顯示一行小字，不擋原本的成功卡；`retry: false`（對不上是確定的答案）。

## 校正：一開始的版本在舊模擬照上不能用
第一版只遮掉標題欄與尺寸標註帶，整張一起比。拿 `eval/drawing_photos/known` 30 張**沒改過**的圖紙照片試：
- 3 張被判成整體變了；
- 另外 3 張冒出假差異。

逐張看疊圖後改了五件事：

1. **只比三視圖的方框**：假差異幾乎都是照片裡紙張的邊緣、牆面。
   拉正後落在圖紙的留白處，`tilt` 照片離圖紙邊緣 25–40 px，最外圈 12 px 的邊界擋不住。
2. **每個視圖各自微調位置**：`make_synthetic_photos.py` 的 tilt 用 PIL 的 QUAD（雙線性），不是相機拍得出來的透視。
   整張共用一個 H 時，邊緣的視圖會差到 25 px。真實照片也會因紙張彎曲、鏡頭變形有類似的局部誤差。
3. **微調只准平移、旋轉，不准縮放**：
   - 一開始用仿射微調，結果它把前視圖橫向拉長 2% 的改動修平成「沒有差異」（微調算出 1.016 倍）。
   - 外形尺寸小改時三視圖的比例只差 1–3%，所以改成剛體。
   - 偵測下限是 3%：300 px 寬的視圖差 9 px；2% 在 3 px 的容許距離內，不論怎麼微調都看不出來。
4. **判「缺少」用寬鬆門檻**：模糊照片裡的點線（隱藏線）變淡，嚴格門檻抓不到，就被當成「缺少」。
   判「多出」仍用嚴格門檻，反光、陰影不會被當成線。
5. **去雜點分兩種**：
   - 「多出」來自照片，線條邊緣常沿著線多一長條 1 px 的鋸齒，用開運算去掉；
   - 「缺少」取自乾淨的知識庫圖紙，尺寸線只有 1 px 寬，開運算會把整條缺少的細線抹掉，所以只去掉 6 px 以下的碎點。

`min_region_px` 由 40 改 30：
- 40 時漏掉 1 處（擦掉一段尺寸線，只剩 35 px）；
- 30 時 39/39 處改動全部找到，假差異和 40 時相同；
- 24 起舊模擬照多 1 處假差異。

**改版素材的字型**：知識庫圖紙是組員在 Mac 上產生的，字型和 Windows 不同。在 Windows 直接重畫 rev.A，
視圖格裡的尺寸數字、視圖標題的筆畫都不同，會被當成差異（實測多 6 處）。所以 rev.A 是兩版都在 Windows 畫一次，
只把兩版不同的地方貼到知識庫的 rev.B 圖紙上（`eval/make_align_photos.py` 的 `rev_a()`）。
這代表一個真實的限制，見下方「限制」。

照片由 `eval/make_align_photos.py` 產生（固定亂數種子，78 張，附在 `eval/align_photos/`），每張都附正確答案；透視用真正的單應矩陣。

| 延遲（對位＋比對，不含讀檔）P50／P95 | 45／82 ms |

## 限制
- **近拍特寫做不到**：拍到長邊 30% 只有 4/10 對得上，20% 以下（例如只拍簽名）在可行性試驗中是 0/30。
  - 瓶頸是知識庫原圖太小（長邊 1024 px，〈谿山行旅圖〉511×1024），不是演算法。
  - 要做特寫，得換高解析原圖並分塊抽特徵（第 4 步）。
- **只適用平面**：畫作、圖紙可以；立體實物對標準圖不在範圍內。
- **外形尺寸**：
  - 改得多（> 約 25% 的線條不同）回 `global_change`：三視圖依外形縮放（`drawing.py` 的 `_scale()`），整張都會不同，請直接比標註尺寸；
  - 比例差 3% 以下看不出來。兩版都在知識庫時，直接比 `geometry` 的數字更準。
- **不同系統出的圖紙**：視圖格裡的尺寸數字、文字只要字型不同就會被當成差異。
  要比的是同一套系統出的新舊版；別家出的圖要先遮掉文字（之後的事）。
- **模擬照不是實拍照**：評估照片都是合成的，真實照片的光線、紙張彎曲、鏡頭變形要等 D 的實拍照再量一次。
- 畫作找不同不在這一步：照片受光線影響大（ADR 010 量過 dim 拍法的色盤色差 8.91）。

## 驗證
- `backend/tests/test_align.py`：
  - 位置：已知 H 的位置框誤差 < 2%；整幅照片涵蓋 > 97%；別幅畫回 None；鏡像回 None。
  - 差異：同一張 0 處；加孔 1 處「多出」且位置對；擦線「缺少」；1 px 尺寸線擦掉找得到；紙張邊緣不算；
    格子外的記號不算；單一視圖偏 (6, 4) px 微調後不算；微調不會吃掉移位的孔；微調不會縮放；3% 拉長找得到；
    模糊的點線不算缺少；外形整個縮放回 `global_change`。
  - 其他：疊圖大小與顏色；`rectify()` 的涵蓋範圍；三視圖方框和 `drawing.py` 一致。
- `backend/tests/test_align_api.py`：
  - 圖紙、畫作的 200 回應與疊圖；
  - 不對的畫作回 `ALIGN_FAILED`；
  - target 格式回 `VALIDATION_ERROR`；三種 404；
  - `/eval/runs` 不被 `-align.json` 弄壞。
- 前端：在內建瀏覽器實際操作——rev.A 照片顯示 3 處差異、沒改過的圖紙顯示「線條一致」、畫作近照的位置框；
  手機寬度沒有橫向捲動。

# ADR 036：展示帳號精簡成五個，主管拿到所有權限、自己超過額度直接生效

- 日期：2026-10-13
- 狀態：採用（分支 `身分調整`）
- 編號：035 是孔位校正；`feat/立體作品` 的 ADR 031 草稿合進 `dev` 時改用 037 以後
- 相關：ADR 011（修改資料流程與主管核准）、014／015（資料範圍與 JWT）、029（藝術家與區域解說）、030（管理畫面只給主管）
- 修訂：ADR 011 的「主管只能核准、不能改資料」「生管開工單與排程」「不能核准自己的申請（主管自己沒有申請）」

## 背景
`shared/access.yaml` 原本有 8 個展示帳號、6 種角色：訪客、倉管・一廠、倉管・二廠、業務・甲、業務・乙、生管、主管、藝術家・甲。
展示時身分選單太長，同一種角色的兩個帳號只差範圍；主管只能核准、收錄，連一筆盤點都不能自己做，
要示範開工單、排程還得切到生管。使用者要求（Q-2026-10-13-01 之後）：

- 訪客改名「一般員工」；倉管、業務各留一個，名稱「倉管」「業務」；刪掉生管；藝術家・甲改名「藝術家」
- 主管要有所有權限

## 決定
1. **5 個帳號**，帳號代號和名稱對得上：`guest` 一般員工、`warehouse` 倉管、`sales` 業務、`manager` 主管、`artist` 藝術家。
   刪掉 `wh2`、`sales_b`、`planner`；`wh1` 改成 `warehouse`、`sales_a` 改成 `sales`。角色代號 `guest` 不變（只改顯示名稱），
   一般員工的權限不變：只能查公開畫作，也還是預設身分。
2. **範圍可以寫 `"*"`＝全部**（倉庫、客戶、畫作）。只剩一個倉管、一個業務，倉管管全部倉庫、業務管全部客戶；
   主管三種範圍都是全部。檢查一律走 `Account.has_warehouse()`／`has_customer()`／`has_artwork()`，
   `/auth/accounts` 照樣回 `["*"]`，前端顯示「全部倉庫」（`api/client.ts` 的 `inScope()`、`scopeLabel()`）。
   範圍檢查的程式不拿掉：要恢復分廠區、分客戶，只要在 `access.yaml` 改回列舉。
3. **主管有所有操作**：原本的核准、收錄、展示還原，加上倉管的盤點／調撥／報廢／改狀態、業務的改訂單、
   生管的開工單／改工單交期／取消工單／排程，以及藝術家的圈區域（全部畫作）。
   **能核准的人（`approve`）可以取消任何人開的工單**；ERP 匯入的既有工單仍然不能用對話取消（那是資料規則，不是權限）。
4. **主管自己超過額度直接生效**。只有一個主管，又維持「不能核准自己的申請」，主管自己報廢 15 件就會卡在待核准、沒人能核。
   改成：能核准的人試算超過額度時 `next` 是 `confirm`（不是 `approval`），`reasons` 照樣列出超額原因，
   訊息寫「超過額度…主管身分直接生效」，前端確認卡標黃；確認寫入時異動紀錄的備註帶「主管身分直接生效（超過額度：…）」，
   稽核紀錄的「寫入」在 `detail.over_quota` 帶超額原因。圖紙頁主管開急件直接開立（稽核同樣帶超額原因）；
   主管呼叫 `request-approval` 回 409 `APPROVAL_NOT_NEEDED`。「不能核准自己的申請」照留，擋的是改版前留下的申請。
5. **硬性上限不變**：單次超過 5 列、庫存變負數、訂購數量少於已出貨、零件主檔與機台資料，主管照樣被擋。
6. 第 1 段「切換成〇〇再試一次」照 `access.yaml` 的帳號順序挑第一個做得到的：查庫存 → 倉管；改訂單 → 業務；
   排程、開工單 → 主管（現在只有主管做得到）。

## 取捨
- **職責分離變弱**：主管自己的超額異動不需要第二個人同意，只靠稽核紀錄事後查。展示帳號只有一個主管，
  不這樣做就是死結；正式版接 SSO、有多個主管時，可以把第 4 點改回「送另一位主管核准」。
- **範圍不符的示範沒了**：README 原本第 27 步「倉管・一廠改二廠庫存 → 資料範圍 ✕」做不出來，改成「主管超額直接生效」。
  範圍檢查的程式還在，測試改用臨時帳號（只管 WH-A 的倉管、只管一個客戶的業務）直接呼叫 `change_service.authorize()`。
- **藝術家的名稱**：區域解說的段落寫成「<帳號名稱>說：「…」」（ADR 029 的 `speaker`）。原本「藝術家・甲」看得出是某位標註者；
  改成「藝術家」之後，模型更可能把它當成畫這幅畫的人。知識庫目前沒有收錄過的區域解說，影響的是之後新收錄的。
- 舊的展示資料：`production.sqlite3` 裡舊帳號（`wh1`、`planner`…）開的工單、申請照樣看得到；`make demo-reset` 會清掉。
  舊的 JWT（`sub` 是已刪的帳號）在閘道回 401 `TOKEN_INVALID`，前端改發一般員工的憑證。
- 驗證：`pytest`（`test_agent.py`、`test_auth.py`、`test_guard.py`、`test_schedule.py`、`test_access_leaks.py` 等）、`npm test`、`npm run typecheck`。

# ADR 013：照片建檔（拍照、擋模糊、人確認後寫進知識庫）

- 日期：2026-10-02（第 2 步：2026-10-03）
- 狀態：採用（demo）。第 1 步圖紙：選項 1、收錄權限給主管（使用者在 2026-10-02 選定）；
  第 2 步畫作：拍畫作本身、資料用跳出的表單填（使用者在 2026-10-03 選定，見文末「第 2 步：畫作」）；
  `make demo-reset` 是否移除照片建檔的資料待決定
- 由來：`問題/專案問題.md` Q-2026-10-02-01 第 2 項的追問（個人工作流程檔，不在 repo 裡）

## 背景
新增一張圖紙現在全靠手動（README「新增一張工廠圖紙（不改程式）」）：照 `part.schema.json` 寫 JSON、寫 CadQuery 標準模型、
`make drawings`、遞增版本、`make index`。「換領域要花多少成本」只回答了程式那一半，建庫那一半還是人工。

照片建檔：拍圖紙 → 本地 Qwen3-VL 依該領域的 schema 讀標題欄 → 規則驗證 → 人確認 → 寫進 `kb/` → 重建索引，
收錄後馬上辨識得出。流程寫一次，換領域＝換一份 schema 與設定。先做圖紙；畫作（展牌）是下一步。

不在這一步：
- 畫作展牌建檔（段落授權只收 CC0／公有領域／CC BY 4.0，展牌解說是館方著作，見文末「畫作」）；
- 一次建一個資料夾、智慧助理「幫我建檔」入口、串 Ortho2CAD 產生標準模型。

## 可行性實驗（2026-10-02，我的筆電：GTX 1650 4 GB、`qwen3-vl:4b-instruct`，暫存區腳本，沒有放進專案）

7 張圖紙（`kb/drawings/mfg-001`～`006`、`kb_staging/drawings/mfg-007`）× 原圖／tilt／glare／blur
（`eval/drawing_photos/known/`），長邊 1024，Ollama `format` 帶 7 個欄位的 JSON schema，`temperature 0`：

| 拍法 | 欄位正確 | 7 欄全對 | 填 null | 抄錯 |
|---|---|---|---|---|
| 原圖 | 48/49 | 6/7 | 0 | 1 |
| tilt | 45/49 | 3/7 | 3 | 1 |
| glare | 48/49 | 6/7 | 0 | 1 |
| blur | 19/49 | 0/7 | 0 | 30 |

- 清楚的 21 張：公司、品名、料號、圖號、版次都是 21/21。
  錯的只有材料的罕見字（「SCM440 鉻鉬鋼」→ 鎖銅鋼、錯鋁鋼、鎢銅鋼，牌號 SCM440 每次都對）與 tilt 時機密等級填 null（3 次）。
- 模糊的 7 張：**一個 null 都沒有，30 格是編的**（`BRK-1001` → `BRL-1001`、`A6061-T6` → `A40K1-T4`），
  機密等級還填了隔壁格的「第一角法」。模型不會說「看不清楚」，所以要在送模型之前擋、輸出之後用規則驗、最後一定要人確認。
- 清晰度（整張照片、長邊 1024 的拉普拉斯變異數，`cv2.Laplacian`）：blur 45–276，其他拍法 924 以上，一個門檻分得開。
  （第 2 步改成「重新模糊法」：拉普拉斯在畫作上分不開，見文末「第 2 步：畫作」。）
- 每張約 32 秒（讀圖 1,220 token 16 秒、輸出約 92 token 13 秒），冷啟動另加 49 秒。建檔不是即時問答，可以接受。
- OpenAI 相容端點（後端實際走的）的 `response_format: json_schema` 也有效，列舉值會被遵守。

## 流程（各選項共用）
```
POST /intake（SSE）
  ① 模糊程度 > intake.max_blur ─► INTAKE_TOO_BLURRY（請重拍，不送模型）
  ② 領域路由＋辨識（identify_any）─► 已收錄 ─► INTAKE_ALREADY_IN_KB（附那張圖紙／那幅畫，不重複建檔）
                                   └► 從圖紙頁進來、路由很確定是畫作（或反過來）─► INTAKE_WRONG_DOMAIN
  ③ Qwen3-VL 讀標題欄（＋三個外形尺寸），response_format 用 JSON schema 限制；列舉值寫成 enum
  ④ 規則驗證：料號／圖號／版次格式、機密等級、料號與圖號不能和知識庫重複、
     材料用「牌號」對照知識庫既有零件校正名稱並補密度（SCM440 → 鉻鉬鋼、7.85）
  ⑤ 草稿存 data/intake/<draft_id>/（照片、拉正後的圖、欄位與每欄的來源：Qwen3-VL／規則／人）
確認頁：照片與欄位並排；模型填的標色、沒過驗證的標紅；照片上沒有的必填欄位（類別、負責單位）由人填
POST /intake/{id}/commit（要有 kb_intake 權限）
  ─► 再驗一次 schema ─► 寫 kb/parts/<id>.json、kb/drawings/<id>.png ─► 遞增 kb/VERSION
  ─► 背景重建索引（同一個行程，沿用已載入的 CLIP、bge-m3）─► 失敗就把寫進去的檔案和版本還原
```
- 存進 `kb/drawings` 的圖：找紙張四角拉正、縮成 800×970、**再依標題欄外框對齊版面**、去陰影成「白底黑線」。
  辨識（ORB 遮罩、`ink_overlap` 的 `gray < 160`）、縮圖、Ortho2CAD 的裁切都假設這個版面，所以只收**同一種版面**的圖紙；
  找不到四角、長寬比不對、或找不到完整的標題欄外框就要求重拍。
  對齊標題欄這一步是做的時候才加的：模擬照的 tilt 在紙張內部做透視，紙張外框拉正後標題欄落在 y≈775–905（版面是 810–952）；
  實拍沒拍滿整張紙時也會這樣。標題欄外框是下方最大的閉合長方形，縮放、平移到 `TITLE_BOX`（`analysis/page.py`）。
  知識庫原圖量到 (24, 810, 777, 953)、版面 (24, 810, 776, 952)；模擬照 glare 7/7、dim 7/7、tilt 6/7 對齊成功，crop 多半找不到（標題欄被裁掉，本來就該重拍）。
- 讀標題欄送的是**原照片**（長邊 1024），不是整理過的圖：實驗用的是原照片；整理後小字變細，沒有量過。
- 提示詞與驗證規則放 `shared/models.yaml` 的 `intake.mfg`（欄位提示、格式）、模糊門檻 `intake.max_blur`；列舉值從 schema 讀。不影響索引，不進 manifest。
- 記憶體管理：新流程 `intake`（Chinese-CLIP＋Qwen3-VL）。
- 草稿和上傳照片一樣保存 7 天。

## 選項：沒有標準模型的零件怎麼收

`part.schema.json` 規定 `cad`（CadQuery 標準模型）必填。外形尺寸、體積、重量（`geometry`）都是建索引時執行標準模型算出來的，
後端的零件列表、圖紙搜尋、問答的零件卡、3D 重建，前端的 `PartCard`、`PartPage` 都直接讀它。照片建檔的零件沒有標準模型。

1. **`cad` 改選填**：`geometry` 只放從圖上讀到的寬、深、高（人確認），體積、重量、標準模型 STL／STEP、IoU 都沒有。
   - 要改：schema（加選填的 `dimensions_mm`、`intake`）、`kb.py`、`build_index`、`make drawings`、`chunking`、`part_card`、
     `part_summary`、API schema（`PartGeometry` 欄位可為 null、`model_url` 可為 null）、模型下載回 404、3D 重建改用圖上尺寸、
     前端 `PartCard`／`PartPage`／`ReconstructPage`、`run_cad_eval` 跳過沒有標準模型的零件、測試。約 25 個檔，共用層要寫 CHANGELOG。
   - 好處：建檔不需要任何額外模型，這台筆電也能完整展示；「人確認過的資料」和「系統算的」分得清楚。
2. **收錄時用 Ortho2CAD 產生標準模型**：其他程式幾乎不用改。
   - 壞處：這台沒裝 Ortho2CAD（模型 6.2 GB）；生成的程式碼可能執行失敗；把模型猜的形狀當「標準」，之後 IoU 是自己比自己，重量也是猜的。
3. **這一步只做到草稿，匯出 JSON 給人補標準模型**：改動最小，但沒有「收錄後馬上辨識得出」的展示效果。

## 決定
- 採用選項 1（使用者選定）。
- 收錄權限：`shared/access.yaml` 新增操作 `kb_intake`，只給主管（使用者選定）。任何身分都能拍照產生草稿。

### 沒有標準模型的零件（選項 1 的實作）
- `part.schema.json`：`cad` 不必填；沒填 `cad` 就必填 `dimensions_mm`（寬、深、高）與 `intake`（`method: photo`、`date`、`draft_id`、`model`、`fields_from_model`、`confirmed_by`）。
- 建索引：只對有 `cad` 的零件執行標準模型；其他零件的 `geometry` 是 `dimensions_mm`，`volume_mm3`／`weight_kg`／`faces` 為 null；
  基本資料段落寫「取自圖上標註（照片建檔，沒有標準 3D 模型，未估算重量）」。
- API：`model_url`、`step_url` 為 null，`/parts/{id}/model.*` 回 404 `PART_MODEL_NOT_FOUND`；`PartSummary.intake`、`PartDetail.intake`。
- 3D 重建：外形依據改用 `dimensions_mm`（「照片建檔時確認的圖上標註」）；沒有 IoU。`make drawings` 略過這類零件；`make eval-cad` 不列入。

### API
| 路徑 | 內容 |
|---|---|
| `POST /api/v1/intake`（SSE） | `{image_id, domain}` → `stage`（圖紙 sharpness／identify／page／read／validate；畫作 sharpness／identify／validate）→ `token`（模型輸出的 JSON，只有圖紙）→ `draft` → `done`；擋下時 `error`（見 `shared/sse_events.md`） |
| `GET /api/v1/intake/{draft_id}` | `IntakeDraft`：每個欄位的值、來源（Qwen3-VL／規則／人）、規則附註、狀態（ok／invalid／missing／empty）、檢查清單、能不能收錄 |
| `PUT /api/v1/intake/{draft_id}` | `{values: {key: 值}}`：人改的欄位來源標「人」，重新套規則與驗證 |
| `POST /api/v1/intake/{draft_id}/commit` | 主管收錄：回傳時 `status: indexing`，背景重建完成後 `done`（或 `failed`：寫進去的檔案與版本已還原，可以改了再收錄） |
| `DELETE /api/v1/intake/{draft_id}` | 捨棄草稿（正在收錄的不能捨棄） |
| `GET /api/v1/intake/{draft_id}/photo.jpg`、`drawing.png`、`image.jpg` | 原照片、要存進知識庫的圖（圖紙是整理後的 `kb/drawings`、畫作是照片本身 `kb/images`），草稿的 `kb_image_url` |

- 模型無法使用（主推論與本地備援都失敗）不算錯：照樣給草稿，欄位全空，由人照著照片填。
- 規則：料號、圖號、版次格式（`intake.mfg.fields.*.pattern`，這座工廠的格式）、機密等級列舉（從 schema 讀）、尺寸與密度範圍、
  料號與圖號不能和知識庫重複；材料依牌號對照知識庫既有零件——**只改模型讀的寫法**（人填的不動）、**補密度**（人填過的不動）。
- 收錄時再驗一次 schema（`kb.part_problems()`）、零件編號再取一次（避開 `kb/` 與 `kb_staging/` 用過的），稽核紀錄記 `op: kb_intake`。
  一次只收錄一張（`INTAKE_BUSY`）；重建後新零件不在索引裡就還原（刪檔、版本改回、再建一次）。
- 收錄寫的段落只有一段「建檔紀錄」（schema 規定至少一段）；製程、檢驗段落要從內部文件補。

### 前端（`/drawings/intake`）
上傳 → 五個步驟逐一亮起、模型輸出的 JSON 逐字顯示 → 確認頁：照片／要存的圖切換、檢查清單、欄位表單（來源標色、沒過驗證標紅、知識庫既有值當選項）
→ 「收錄進知識庫」只對有 `kb_intake` 的身分可按（後端仍會檢查），其他身分顯示「請切換成主管」→ 重建期間每 1.5 秒重抓 → 完成後連到圖紙頁。
入口：智慧助理附照片辨識不到時，回答下方的「拍照建檔：這是一張圖紙」（只給能用工廠領域的身分），以及圖紙辨識拒答頁的「把這張圖紙建進知識庫」，都帶 `?image=` 直接開始（原本的圖紙首頁入口隨統一入口 ADR 016 拿掉）。零件卡、圖紙頁、3D 重建頁顯示「照片建檔」與沒有重量／3D 模型。

### 校正（第一次跑 `20261002T161444-ce0a`）
擋下 14 張，264＋44 格裡 287/308 正確、**8 格錯了卻通過驗證**：
- 6 格是品名少了空格：「L 型固定支架」抄成「L型固定支架」（〈T 型槽螺帽〉同樣）。字是對的，但和知識庫寫法不同，搜尋、比對重複時會對不上。
  知識庫裡英數字和中文之間一律有空格（沒有任何一個黏在一起）→ 規則補空格（`intake_service._spacing()`，料號與列舉值不動）。
- 2 格是一張裁切照（mfg-005 crop）的標題欄左邊被裁掉，公司讀成「容機械（虛構）」、品名讀成「型槽螺帽」。
  標題欄外框貼到圖的邊緣 → 當作沒拍完整、請重拍（`page.title_block_box()`）。代價：多擋下 3 張 tilt（模擬的 tilt 拉正後外框貼邊）與 1 張 crop。
- 兩個修正之後，用第一次跑的模型輸出離線重算與重跑（溫度 0，輸出相同）結果一致：錯了卻通過驗證 8 → 0。

## 限制
- 只收和知識庫圖紙同一種版面（800×800 三視圖＋170 px 標題欄）的圖紙；其他版面要先加版面設定。
- 模擬照的 tilt 是在紙張內部做透視，拉正沒辦法用它驗證；要用實拍照片校正四角偵測。tilt 照片 7 張擋下 4 張，實拍時擋下的比例可能不同。
- 模型讀錯但格式正確的值（例如把 D-24-0502 讀成 D-24-0802）規則擋不下來，只能靠人確認；這次評估裡沒有出現，但模糊照實驗裡有（所以糊照一律擋）。
- 只有 7 張圖紙、都是同一座虛構工廠的同一種字型與版面，數字不能直接推到真的工廠圖紙。

## 第 2 步：畫作（2026-10-03）

使用者要求：「畫作模組也要可以拍照建檔，一樣太模糊直接擋住，資料標籤採取跳出表單填寫的方式」。

### 決定
- **拍畫作本身，不讀展牌**：資料由人在跳出的表單填，不送模型。
  原本打算讓模型讀展牌，但展牌解說是館方著作（段落授權只收 CC0／公有領域／CC BY 4.0）、各館版面不同、手上也沒有展牌照片可以校正。
- **照片本身就是知識庫的原圖**（長邊 1024，和 `kb/images` 相同）：之後辨識（CLIP＋ORB）、色彩分析都用它；建索引時色彩分析自動算。
  沒有做自動裁切：牆面與畫框的對比因館而異，模擬照驗不出來；請使用者正面拍、畫面盡量只有畫。
- **一樣先擋模糊**，兩個領域共用一個門檻（`intake.max_blur`），見下面「模糊門檻」。
- 表單欄位（`shared/models.yaml` 的 `intake.art.fields`，`group` 分區）：
  - 基本資料：畫名＊、英文畫名、作者＊、作者英文名、年代＊、材質、尺寸、風格標籤（頓號或逗號分隔）；
  - 典藏與授權：典藏單位＊、館藏編號、典藏頁網址＊（`source_url`，資料出處）、照片授權＊（白名單三選一）、照片標示文字（CC BY 4.0 時必填）；
  - 介紹（選填）：介紹（至少 20 字）、出處網址與授權（填了介紹就必填）、標示文字（CC BY 4.0 時必填）；
  - 知識庫 ID：來源代碼＊、編號＊。
- 規則：
  - 來源代碼：典藏單位和知識庫既有畫作相同就沿用它的代碼（國立故宮博物院 → `npm`、The Met → `met`），否則用預設 `photo`；
  - 編號：取館藏編號去掉符號轉小寫（`JP1847` → `jp1847`），沒有就用該代碼的下一個號碼；人改過就不再自動帶；
  - 擋重複：ID 已被 `kb/` 或 `kb_staging/` 用過、畫名＋作者和知識庫既有畫作相同；
  - 英數字與中文之間補空格（和圖紙同一條規則，人填的也套用）。
- **沒填介紹，系統寫一段「基本資料」**：只寫表單上的事實（畫名、作者、年代、材質、尺寸、典藏單位，及照片建檔的日期與確認人），
  授權標 CC0（系統自己寫的文字）、出處是典藏頁。`artwork.schema.json` 加選填的 `intake`（`generated_description` 記下這段是系統寫的）。
- 從哪一邊進來就指定領域（`POST /intake` 的 `domain`）：路由很確定是另一個領域時回 `INTAKE_WRONG_DOMAIN`，頁面帶著同一張照片轉過去；
  路由拿不準（`uncertain`）時照指定的領域辨識。
- 收錄權限、重建索引、失敗還原都和圖紙相同；草稿的 `part_id`／`drawing_url` 改成通用的 `item_id`／`kb_image_url`／`item_url`。
- 前端：`/artworks/intake`（入口：智慧助理附照片辨識不到時的「拍照建檔：這是一幅畫」、畫作辨識拒答頁；尋畫首頁已隨 ADR 016 拿掉），草稿一建好就跳出表單（原生 `<dialog>`）；
  存好且全部通過就關掉，頁面顯示摘要與「編輯資料」；`/drawings/intake` 照舊在頁面上確認。

### 模糊門檻：拉普拉斯變異數 → 重新模糊法
拉普拉斯變異數在畫作上分不開（2026-10-03，`eval/photos` 的模擬照）：模糊照 51–294，但〈谿山行旅圖〉清楚、偏暗的照片只有 125
（水墨低對比、留白多）。改用 Crété-Roffet 等人（2007）的無參考模糊指標（`page.blur_score()`）：
把照片再模糊一次，量相鄰像素的差異還剩多少沒被抹掉——已經糊掉的照片再模糊也變化不大。和畫面內容、明暗、對比無關：

| | 模糊照 | 其他拍法（tilt／glare／crop／dim）與知識庫原圖 |
|---|---|---|
| 畫作（`eval/photos`、`kb/images`） | 0.361–0.430 | 0.128–0.265 |
| 圖紙（`eval/drawing_photos`） | 0.345–0.448 | 0.069–0.143 |

門檻 0.30 兩個領域共用；圖紙改用新指標後，擋下的照片和原本一樣（模糊照全擋、其他拍法不擋）。
`make eval-intake`（`20261002T180328-4216`）每次都會重算畫作這段：`eval/photos` 的 blur 5/5 擋下（0.361–0.430）；
crop、dim、glare、tilt 各 5 張與 10 張原圖都不擋（最高 0.265）。

### 限制
- 照片就是知識庫的原圖：斜拍、反光、拍到畫框和牆，之後的辨識與色彩分析都會受影響；只靠拍照提示，沒有自動裁切。
- 系統寫的「基本資料」只有事實，問答答得出作者、年代、典藏，但答不出技法與背景；介紹要從開放授權的來源補。
- 「畫名＋作者」相同才算重複：同一幅畫寫法不同（例如換了譯名）擋不住，靠以圖辨識那一關。

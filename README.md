# 地端隱私多模態 RAG 專題 — 畫作導覽助理＋工廠機械加工圖助理＋庫存 Text-to-SQL＋生產排程（Demo）

拍下或上傳一幅畫 → 系統辨識是哪幅畫 → 依畫作知識庫以繁體中文回答，每句附出處。
**同一套架構換一個知識庫**：拍下一張工廠加工圖 → 辨識是哪張圖紙 → 用 **Ortho2CAD** 把三視圖還原成
可編輯的 CadQuery 程式碼與 3D 模型 → 依製程與檢驗規範回答問題。圖紙屬企業機密，全程不出本機。
工廠的**庫存、工單與客戶訂單**則放在本機的關聯式資料庫，用中文提問 → 本地模型寫成 SQL → 唯讀執行 → 依結果回答
（**文件走 RAG，數字走資料庫**，見 ADR 004）。
**圖紙、資料庫、生產排程是一個整合系統**：查到圖紙 → 依庫存缺口在圖紙頁開立工單 → **Timefold Solver** 把工單的工序
（來自圖紙的「加工製程」段落）排上機台、兼顧交期與換線 → 排程結果寫回資料庫，Text-to-SQL 查得到（ADR 005）。
16 GB 展示機記憶體使用率超過 80% 時，自動釋放目前流程用不到的模型（ADR 006）。
**智慧助理（統一入口）**：每句話依序經過**七段權限控管**（ADR 015）——① 認證與授權（API 閘道驗 **JWT** 簽章與效期，
沒帶、竄改、過期一律 401；再用憑證的角色檢查要做的事）→ ② Jev 意圖路由／防護欄（**Jev Choice**：正常查詢／Prompt 注入／
無關閒聊，閒聊快速短路）→ ③ 權限感知檢索（Metadata Filter 只照 JWT 產生）→ ④ **Jev Noul** 雙重驗證（is_relevant、
security_leak_check）→ ⑤ **Jev Score** 評分重排（最多 3 段）→ ⑥ 生成閘門（權限內查無答案就降級回「查無資料」，
不透露有文件但沒有權限）→ ⑦ 本地 LLM 生成。只有第 2、4～6 段會把**代號化**內容送 TypeSafe **Jev**，機密段落不出廠；
**修改庫存、訂單、工單一律經過權限判定**，超過額度送主管核准（ADR 011）。
架構依《地端隱私多模態 RAG 專題開發企劃書》，主打**地端部署＋資料隱私**：**混合式為主**（本地 JSON 知識庫＋
本地向量檢索＋本地 VLM，照片與知識全程不離開主機）、**雲端 API 只當對照組**（A1 無檢索、A2 有檢索，
預設關閉）、**LoRA 保留插槽**。各策略共用同一個檢索層與 prompt，只換生成端。

## 快速開始（macOS／WSL2）

需要：[uv](https://docs.astral.sh/uv/)、Node.js 24、[Docker](https://docs.docker.com/get-docker/)（資料庫；沒有也能跑，見下方「資料庫」）、
[Ollama](https://ollama.com)（沒有也能跑，見下方 mock 模式）

```bash
make setup      # 安裝套件、建立 .env、下載 qwen3-vl:4b-instruct
make db-up      # 啟動資料庫容器（PostgreSQL 17 + pgvector），等到可以連線才結束
make index      # 驗證知識庫、建索引並寫進資料庫（第一次會下載 Chinese-CLIP 約 750 MB、bge-m3 約 2.2 GB）
make demo       # 建置前端並啟動 http://localhost:8000
```

開發時用 `make dev`（後端 8000 熱重載＋前端 5173，Vite 把 `/api` 代理到後端）。

**工廠圖紙的 3D 重建（Ortho2CAD）**另需 llama.cpp 與約 6.2 GB 模型（Ollama 目前不能載入這個模型）：

```bash
brew install llama.cpp
make ortho2cad-setup   # 下載 Q4_K_M 語言模型（5.0 GB）＋視覺權重（1.15 GB），轉成 mmproj
make demo-all          # 同時啟動 Ortho2CAD（:8081）、排程服務（:8082）與展示伺服器（:8000）
```

Ortho2CAD 以 llama-server 的 router 模式啟動（`deploy/llama-router.ini`）：第一次 3D 重建時才載入模型，
記憶體吃緊時可卸載、下次用到再自動載入，產生的程式碼與原本逐字相同。

**生產排程（Timefold Solver）**另需 Java 21（約 200 MB；Maven 由設定腳本從 Maven Central 下載，約 9 MB）：

```bash
brew install openjdk@21        # Ubuntu／WSL2：sudo apt install openjdk-21-jdk-headless
make scheduler-setup           # 下載 Maven 與 Timefold 等套件、跑 Java 單元測試、建置 scheduler/target/scheduler.jar
make scheduler                 # 另開終端機啟動 :8082（make demo-all 會一起啟動）
```

沒有 Java 時排程頁自動改用簡易排程（交期優先派工，畫面標示「未最佳化」），其他功能不受影響。

沒有 Ortho2CAD 時圖紙辨識與問答照常可用，3D 重建頁會提示啟動；`LLM_MODE=mock` 時回傳標準模型的程式碼。

**沒有 GPU／模型的電腦**：在 `.env` 設 `LLM_MODE=mock`（不呼叫生成模型）；
再加 `EMBED_MODE=mock` 連 embedding 也不下載（只能測流程，辨識結果無意義），改完要 `make index`。

### 資料庫（PostgreSQL 17 + pgvector，Docker）

照企劃書 §七：資料庫進 Docker（`deploy/docker-compose.yml`），Ollama 原生安裝在主機上，後端與前端在本機熱重載。
畫作、段落、向量、索引 manifest 與使用紀錄都存在資料庫；縮圖與標準模型的 STL／STEP 仍是 `data/index/` 下的檔案。
資料庫只綁 `127.0.0.1`，不對區網或公網開放；資料放在 Docker volume `artrag_pgdata`，容器刪掉重建資料還在。

| 指令 | 用途 |
|---|---|
| `make db-up` | 啟動資料庫，等到可以連線才結束 |
| `make index` | 建索引；`.env` 設了 `DATABASE_URL` 會在同一個交易裡寫進資料庫，執行中的後端自動換上 |
| `make index-db` | 不重算向量，把現有的 `data/index/` 寫進資料庫（剛裝好 Docker 時用） |
| `make db-import-sqlite` | 把 `data/artrag.sqlite3` 的舊紀錄（上傳、問答、3D 重建、庫存查詢、智慧助理路由、回饋）搬進資料庫；重複執行不會重複寫入 |
| `make db-psql` | 進資料庫下 SQL，例如 `SELECT id, title_zh, license FROM artworks;` |
| `make db-stop` | 停止資料庫（資料保留） |

Windows 沒有 `make` 時，在專案根目錄用 PowerShell：

```powershell
docker compose -f deploy/docker-compose.yml --env-file .env up -d --wait db
cd backend; uv run python ..\pipelines\build_index.py --db-only
uv run python ..\pipelines\import_sqlite_logs.py
```

**沒有 Docker 的電腦**：`.env` 的 `DATABASE_URL` 留空，改用檔案索引（`data/index/`）＋SQLite（`data/artrag.sqlite3`），
功能相同（見 ADR 001、009）。兩種方式的檢索結果由 `backend/tests/test_postgres.py` 比對一致；
這個測試要 `TEST_DATABASE_URL` 指向一個可以清空的資料庫才會跑，CI 用 pgvector 容器跑。

### 組員：建立自己的資料庫

企劃書 §六：**不互傳資料庫**，每個人用同一個指令從 `kb/` 的 JSON 重建，manifest 一致才算通過。
每人一個資料庫，誰重建索引都不會影響別人。在 `make setup` 之後：

1. **安裝 Docker Desktop**。
   - macOS：直接安裝。
   - Windows 照《部署說明》在 WSL2 的 Ubuntu 裡開發：裝好後到 Docker Desktop 的
     Settings → Resources → WSL integration 打開 Ubuntu，Ubuntu 裡才有 `docker` 指令。
2. **確認 `.env` 有 `DATABASE_URL`**。`make setup` 由 `.env.example` 複製，預設已填好。
   舊的 `.env` 不會被覆蓋，要自己從 `.env.example` 補上「資料庫」那一段。
3. **`make db-up`，再 `make index`**。
4. （選用）**`make db-import-sqlite`**：部署包附的預跑 3D 重建結果記在 `data/artrag.sqlite3`，
   搬進資料庫後，圖紙頁的「最近的 3D 重建」才看得到（結果和上傳照片一樣只保留 7 天）。
5. **確認建好**：開「系統狀態」頁，「索引一致」要打勾，知識庫版本要和其他人相同（例如 `2026.10.1`）。
   模型版本鎖在 `shared/models.yaml`，embedding 一律用 CPU 算，所以各自建出來的內容相同。

**直接在 Windows 執行（不在 WSL 裡）時**：`make index` 可以照常重建（Windows 沒有 `resource` 模組，
知識庫自己的標準模型改成不限制 CPU 與檔案大小執行）；但 Windows 限制不了子行程，**模型產生的 3D 重建程式碼
要在 WSL2 執行**：在 Ubuntu 裡建一個只有 CadQuery 的環境，`.env` 設 `CAD_WSL_PYTHON`（做法見 `docs/5070ti-host.md`，
ADR 027）；沒設時一律拒絕執行。沒有 `make` 時：
`cd backend; uv run python ..\pipelines\build_index.py`。

**要把使用紀錄給別人**（例如問答紀錄給 D 做評估）：只匯出紀錄表，對方還原到另一個資料庫，不會蓋掉自己的紀錄。
紀錄裡有使用者的問題與回答，請私下傳，不要貼在群組。

```powershell
# 匯出：先寫在容器裡再複製出來（Windows PowerShell 用 > 轉存會把二進位檔改壞）
docker exec artrag-db-1 pg_dump -U artrag -d artrag -Fc -t chat_logs -t cad_logs -t sql_logs -t route_logs -t feedback -f /tmp/artrag-logs.dump
docker cp artrag-db-1:/tmp/artrag-logs.dump ./artrag-logs.dump

# 對方還原到另一個資料庫
docker exec artrag-db-1 createdb -U artrag artrag_logs_from_teammate
docker cp ./artrag-logs.dump artrag-db-1:/tmp/
docker exec artrag-db-1 pg_restore -U artrag -d artrag_logs_from_teammate /tmp/artrag-logs.dump
```

- **`.env` 不要傳給別人**：裡面是個人設定，填了雲端對照組的話還有 API 金鑰。組員照 `.env.example` 建自己的。
- **不要讓組員直接連你的資料庫**：資料庫刻意只綁 `127.0.0.1`；共用一個的話，任何人重建索引都會改到所有人的資料。

## 展示腳本（約 8 分鐘）

**入口＋工廠／藝術模組（ADR 032，介面來源 `ArtRAG-前端demo/` 整合版）**：首頁是入口，左側是可收合的對話紀錄（手機是抽屜）。
找畫、問畫作、圖紙、3D 重建、庫存、排程、改資料都在輸入框說一句（＋ 可附照片），由七段權限控管判斷交給哪個功能；
入口只回簡介與對象縮圖，分派到工廠或藝術時下方出現「進入工廠模組」「進入藝術模組」。模組左邊延續同一段對話，
右邊的展示區大張顯示成果（圖紙、3D、庫存／查詢、排程；作品、細看、年表、相似作品），下方縮圖可以切回之前的成果（← →），
中間分隔線可以拖曳、雙擊回到一半。藝術模組的細看、年表、相似作品是替代展示（人類 2026-10-09 接受）：
細看是段落＋色塊分布＋縮放，沒有畫上熱點；年表是館藏作品依年代排列＋創作背景，不是畫家生平；
相似作品依風格標籤與媒材做文字搜尋，不是影像相似度。後端缺口見 ADR 032。回答下方的「在功能頁打開」連結（例如「打開〈畫名〉」「繼續問這幅畫」「看照片辨識細節」
「打開生產排程」）和模組右上的「功能頁」打開原本的完整頁面，網址不變。下面寫「按〇〇」的都是這些按鈕。

| # | 展示項目 | 操作 | 對應驗收目標 |

### 智慧助理：七段權限控管＋權限與主管核准（約 5 分鐘）

**先在 `.env` 設 `DEMO_CONTROLS=true`**（預設關閉，docs/adr/030）：切換身分不用密碼，所以只在展示模式、本機（`DEMO_TRUSTED_HOSTS`）、
而且已經有憑證時開放，頁首會標「展示模式・不可用於正式環境」。從別台電腦（例如手機）展示時，把那台的位址加進 `DEMO_TRUSTED_HOSTS`。
入口首頁的「試試防護架構」與「展示腳本」按鈕會自動切換身分並送出（展示腳本只有展示模式才出現）；
也可以在右上角的身分選單手動切換，對話裡會留一行「已切換身分為〈…〉」，其他身分查到的內部資料會收起來。
系統狀態頁（最近的問答、SQL、路由紀錄、模型端點）、拒絕並記錄、稽核紀錄只有主管看得到。
身分選單上方列出「JWT · clearance · 部門 · 到期時間」；JWT 在 HttpOnly cookie，畫面與瀏覽器紀錄都讀不到、不保存。
每則回覆上方的處理軌跡列出七段（認證授權 › Jev Choice › Metadata Filter › Jev Noul › Jev Score › 生成閘門 › 本地 LLM）與外送量，
點「處理細節」看每一段的檢查、Metadata Filter、每個候選段落的去留與分數；「技術細節」再看 JWT payload、意圖機率、送給 Jev 的代號化內容與請求本文。
對話紀錄只存公開資料（畫作問答與以文搜畫）；工廠內部資料只存編號，重新整理後由展示區以目前身分重新讀取或重新查詢。
叫不到 Jev（斷網、逾時、回錯誤、沒金鑰）時自動改用地端規則（外送 0），沒有手動切換。

### 干擾段落題（ADR 019）

`qa.jsonl` 的 `type: distractor` 題目會把干擾段落注入檢索結果，再照常經過洩密掃描與段落篩選。
**後端要在 `.env` 設 `EVAL_INJECTION=true`**（預設 false，正式服務不要開），否則這幾題回 403、記為錯誤。
干擾分兩種：`counterfactual`（手寫、和正確答案衝突、掛在同一幅畫底下）、`other`（自動取別幅畫最像的段落）。

2026-10-05 在 5070 Ti（8B）上的 6 題示範題（run_id `20261005T033938-97d3`）：段落篩選開時擋下 4/6、被帶偏 2/6，
關時擋下 0/6、被帶偏 3/6。別幅畫的段落都擋得掉；**同一幅畫、內容錯的段落大多擋不掉，模型會照著錯的回答**
（〈有絲柏的麥田〉答成 1979 年取得）。逐題見 ADR 019。

改用 `rearrange_v2`＋`answer_v2`（ADR 020：矛盾的段落一起留下、回答時明白指出說法不一致）後：被帶偏 2/6 → **1/6**、
指出矛盾 0 → 2/6、整體答對 92% → **96%**，一般題維持 100%（run_id `20261005T042545-369c`）。

工廠圖紙另有 6 題干擾段落題（`part_id`）：`drawing_v1` 被帶偏 0/6、指出矛盾 1/6；改用 `drawing_v2` 後
被帶偏 0/6、**指出矛盾 3/6**（3 題錯誤數值都提醒「說法不一致，現場以正式圖紙與規範為準」）。有圖紙題時 `run_eval.py` 會切成主管身分。

**「看起來可以並存」的矛盾**（ADR 028，`python eval/run_conflict_eval.py`）：模型常把只會發生一次的事寫成兩件都發生過
（「1958 年與 1962 年分別由李霖燦與張大千發現」）。另請看不到 prompt 的代理出 25 題（12 題互斥、9 題其實相容、
4 題知識庫本身就有相近但不衝突的事），分成調整用與保留題。改回答 prompt 的三個版本都沒有穩定變好；
改成**回答前另外只問本地模型「這幾段有沒有互相矛盾」**，有的話在參考資料後面加一句提醒（`conflict_check`，預設開）：

| 篩選開（預設） | 關檢查 | 開檢查 |
|---|---|---|
| 互斥 12 題指出不一致（其中保留題 6 題） | 6（2） | **9（5）** |
| 相容 9 題＋天然 4 題誤報 | 0 | 1 |

### LoRA 不檢索對照組（`make eval-lora`，ADR 043）

負面對照：把畫作知識訓練進權重（LoRA），能不能取代檢索？三組都是 Qwen3-VL 4B、Q4_K_M、temperature 0，
接同一個 llama-server :8081，只差模型別名：

| 策略 | 模型 | 檢索 |
|---|---|---|
| `hybrid` | art-base | 開 |
| `hybrid_norag` | art-base | 關 |
| `lora_norag` | art-lora | 關 |

**做法**（在 Apple Silicon 的 Mac 上，步驟細節見 `pipelines/lora/Makefile`）：

1. `make -C pipelines/lora setup base`：建 `pipelines/lora` 的 uv 環境（mlx-vlm，不動 backend 依賴、不進 CI），
   下載語言層 4-bit 的 MLX 底模與官方 mmproj。
2. `make lora-data`：只用 `kb/artworks` 產生訓練資料到 `data/lora/`。
   - 題型：fact 約 75%、refusal 約 15%、retain 約 10%；
   - 和 `eval/qa*.jsonl` 做字元 3-gram Jaccard 外洩檢查，超過 0.5 刪掉；
   - `review.jsonl` 是兩成抽樣，給組員 D 抽查。

   工廠圖紙不進權重：Metadata Filter 只管得到檢索，管不到權重。
3. `make -C pipelines/lora speed train select export-base export-lora info`：
   - 先跑 20 步量速度，再訓練 QLoRA；
   - 用 dev 題挑 epoch；
   - fuse＋de-quantize → GGUF Q4_K_M；
   - 最後記下三個 GGUF 的 SHA-256。

   訓練時關掉 Ollama、Ortho2CAD 與後端，Air 要接電源。
4. 另開兩個終端機啟動 llama-server 與評估用後端（生成端設定由 Makefile 的 `LORA_EVAL_ENV` 帶入，不改 `.env`），再跑評估：

```sh
make -C pipelines/lora serve   # 終端機 1：llama-server :8081（art-base、art-lora）
make eval-lora-backend         # 終端機 2：後端 :8000，不連 PostgreSQL／Redis、關掉記憶體管理
make eval-lora
```

`make eval-lora` 有三步：
- **問答與亂編率**：`qa.jsonl`；知識庫外畫作的題目不帶畫作送出。
- **遺忘**：`qa_visual.jsonl` 加 20 題一般常識 `qa_general.jsonl`。
- **知識更新**：暫存副本改 5 個事實後重建索引。

done 事件顯示落到備援模型的題目一律記錯；`lora_norag` 只要有一題落到備援或出錯，指令就失敗。

**結果**（2026-10-22，MacBook Air M5，合併進 dev 後 commit `7cb697c` 的 `20261022T115429-0d51`、`20261022T120048-31c5`、`20261022T120517-bab6-kbupdate`；細節與解讀見 ADR 043「結果」）：

| 指標 | hybrid | hybrid_norag | lora_norag |
|---|---|---|---|
| 正確率（test 一般題，12 題） | **75%** | 17% | 50% |
| 亂編率（5 題） | **0／5** | 3／5 | 5／5 |
| 知識更新：新／舊答案（5 題） | **5／0** | 0／0 | 0／3 |
| 遺忘：一般常識（20 題） | — | 70% | 30% |
| P95 首字／完整回答 | 7.9／8.6 秒 | 3.1／3.2 秒 | 6.5／6.9 秒 |

訓練 542 筆（每段 20–30 種問法）、4 epochs、186.9 分鐘，尖峰記憶體 13.5 GB，adapter 132 MB。LoRA 記住了一部分畫作事實，但會亂編、改了知識庫跟不上、一般常識變差：權重裡的知識不能取代檢索。hybrid 照主方案開著檢索段落篩選與問題前提檢查，有 3 題 test 一般題被篩掉正確段落，前提檢查每題多一次地端呼叫；lora_norag 多出的延遲是第 2 段地端判斷要換到 art-base。資料只有 3 幅畫，結果只證明流程能運作，不作為一般結論。

### 背景工作（3D 重建與排程，Redis＋Celery＋PostgreSQL，ADR 041）

3D 重建與排程求解不再綁在 API 行程與瀏覽器連線上：`POST /api/v1/cad/jobs`、`POST /api/v1/schedule/jobs` 回
`202`＋`job_id`，由獨立的 worker 行程執行；進度事件存在 PostgreSQL（`GET /jobs/{id}/events`，可用 `Last-Event-ID`
續接，也能輪詢 `GET /jobs/{id}`），離開頁面不會取消、重新整理會接回。排程有兩個不同的操作：**提前結束**
（`POST /schedule/stop`，採用目前最佳的合法解並寫回）和**取消**（`POST /jobs/{id}/cancel`，放棄、不寫回）。

```bash
brew install redis postgresql@17   # 只在「跑測試」時需要；開發用 make jobs-up 的容器
make jobs-up         # PostgreSQL 與 Redis 容器（只綁 127.0.0.1）
make jobs-migrate    # 版本化 migration（可重複執行）；回復：cd backend && uv run python -m app.jobs.admin rollback
make worker-gpu      # 另開終端機：3D 重建（同時最多 JOBS_GPU_SLOTS 個，預設 1）
make worker-schedule # 另開終端機：排程求解
make demo            # 或 make demo-all：Ortho2CAD、排程服務、兩個 worker 與展示伺服器一起啟動
make jobs-status     # migration 版本、各狀態工作數、待投遞數
make test-jobs       # 背景工作的測試：自己建立隔離的 PostgreSQL＋Redis＋獨立 worker 行程
```

`.env` 的 `REDIS_URL` 和工作資料庫（`JOBS_DATABASE_URL`，留空沿用 `DATABASE_URL`）都有值才啟用。沒有啟用時建立工作回
`503 JOBS_UNAVAILABLE`（**不會**偷偷改在 API 行程執行），舊的 SSE 入口（`/cad/reconstruct`、`/schedule/solve`）照舊可用
（`LEGACY_SYNC_JOBS=auto`）；啟用之後舊入口預設關閉（409 `USE_JOBS_API`），設 `LEGACY_SYNC_JOBS=on` 可以保留。
前端的 3D 重建與排程一律走背景工作，所以展示時要先 `make jobs-up`／`jobs-migrate` 並啟動兩個 worker。
worker 掛掉或重啟：租約過期後工作自動回佇列、**整個重新執行**（不是從模型生成中段續跑），最多 `JOBS_MAX_ATTEMPTS` 次。
Redis 重啟或訊息遺失：outbox 與補投遞會再送；PostgreSQL 重啟：連線池自動重建，期間回 503。
排程已寫入生產資料庫、工作卻來不及標成成功（工作資料庫斷線、worker 當掉）：不會變成「失敗」，恢復迴圈依生產資料庫補做結案，
排程與稽核各只有一筆。照片來源的 3D 重建工作，讀取權跟著照片目前的分享名單（撤銷分享後，建立工作的人也讀不到）。
Redis 不通或剛重啟時無法確認其他行程在用哪些模型，記憶體管理不卸載 Ollama、llama-server、Timefold 上的模型（`GET /memory` 的 `coordination` 會標出降級）。
舊上傳照片、舊 3D 重建資料夾沒有擁有者時預設拒絕，管理者用
`python -m app.jobs.admin adopt-uploads --owner <帳號>`／`adopt-cad --owner <帳號>` 遷移。
